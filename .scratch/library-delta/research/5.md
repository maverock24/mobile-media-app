## Q30

The only cancellation of a native scan is in `scanNativeAudioFiles`'s own
`finally`, `src/lib/browse/folderScan.ts:91-99`, guarded by `scanId && !scanCompleted`
at `:92`. `scanCompleted` starts false (`:62`) and is assigned only from a resolved
batch's `done` flag at `:86`, so the `cancelAudioScan` call at `:94` fires exactly
when the `while` loop (`:70`) is left by an exception: a rejecting
`getAudioScanBatch` (`:74`), or a throw from `onBatch` (awaited at `:79`). A
rejected `startAudioScan` (`:67`) leaves `scanId` as `''` and therefore cancels
nothing. A scan that ends normally is never cancelled. This is pinned by
`tests/unit/browse/folderScan.test.ts:143-159` (no cancel on completion) and
`:197-215` (cancel on batch rejection, cancel failure swallowed).

There is no path that cancels a running session from outside this function. The
only call sites of `DirectoryReader.cancelAudioScan` in `src/` are the declaration
at `src/lib/native/directory-reader.ts:50` and `src/lib/browse/folderScan.ts:94`.
Nothing calls it on unmount, on a new scan, on app backgrounding or on a library
switch. On the native side, `cancelAudioScan`
(`android/app/src/main/java/com/maverock24/mobilemediaapp/DirectoryReaderPlugin.java:214-221`)
only removes the session from the static map, and `getAudioScanBatch` removes it
itself when the queue drains (`:201-204`).

## Q31

A second `startLibraryScan` is not prevented and does not cancel the first.
`startLibraryScan` (`src/lib/device/deviceLibrary.svelte.ts:161`) has no check on
the in-flight state; it assigns `libraryScanPromise = scanPromise` at `:190`,
replacing the first promise. The first scan's batch callback then fails its own
identity test `libraryScanPromise === scanPromise` (`:177`), so it stops writing
`allFiles` and `scanProgress` (`:178-182`) while continuing to await batches from
its still-live native session. Its completion handler returns early at `:193`, so
the first scan writes no cache and hydrates no queue either; the `finally`
(`:202-207`) only clears the field when it still owns it. The net effect is that
the first native session drains to `done` and its files are discarded, not
cancelled.

Not every start is guarded the same way. The first-search effect checks
`!deviceLibrary.libraryScanPromise` before starting
(`src/lib/components/views/Mp3PlayerView.svelte:344-347`).
`rescanCurrentLibraryIndex` (`src/lib/device/deviceLibrary.svelte.ts:210-226`) and
the cache-miss branch of `restoreLocalLibrary` (`:262`) do not check, so a rescan
during a running scan overwrites the promise and discards the earlier scan. Each
deck owns its own `createDeviceLibrary` instance
(`Mp3PlayerView.svelte:415-447`), so this is per deck.

## Q32

Nothing in the app stops or resumes a scan on screen, app or deck changes.
There is no app-state wiring at all: the only Capacitor packages in
`package.json:53-57` are `@capacitor/android`, `@capacitor/core`,
`@capacitor/filesystem`, `@capacitor/haptics` and
`@capawesome/capacitor-file-picker`; `@capacitor/app` is absent and no
`appStateChange` listener exists anywhere in `src/`.

The mount restore effect (`Mp3PlayerView.svelte:1539-1603`) only restores from
cache and sets `isRestoring` (`:1540`, cleared in the `finally` at `:1599-1600`).
The rescan listener (`:1606-1611`) starts a rescan and never stops one. The
`focus` / `visibilitychange` handlers installed at `:1524-1529` call
`handleFocusRestore` (`:1505-1522`), whose only action is
`folderPicker.restorePendingDriveFolderPickerIfNeeded()`; no scan is touched. The
component-destroy cleanup (`:1613`) calls `player.destroy()` and
`audioCtx?.close()` only, with no `cancelAudioScan`, so an in-flight scan keeps
polling batches after unmount and its callbacks keep writing the deck's `$state`
closure.

A deck change is not a remount: both decks stay mounted at all times and are only
hidden with `class:hidden` (`src/routes/+page.svelte:206`, `:231-236`), so
switching A/B never interrupts a scan.

## Q33

Two native scans of the same tree can run at once, and nothing stops them from
colliding at the protocol level. Each `startAudioScan` allocates its own
`UUID.randomUUID()` and stores it in the static `ConcurrentHashMap` at
`DirectoryReaderPlugin.java:129-131` (`AUDIO_SCAN_SESSIONS`, `:42`), so session ids
never collide, but there is no per-tree or global guard and the plugin will hold
two sessions walking the same tree. The index scan
(`src/lib/device/deviceLibrary.svelte.ts:176`) and the folder-play scan
(`Mp3PlayerView.svelte:1172-1177`) both reach `startAudioScan` this way.

What actually keeps them apart is bookkeeping on the JS side, and only partly.
`queueSessionId` (`Mp3PlayerView.svelte:1104`, guard at `:1149-1151`) stops a
still-streaming folder scan from appending to a replaced queue. On the index side,
the `libraryScanPromise === scanPromise` check
(`deviceLibrary.svelte.ts:177`, `:193`) stops a superseded index scan from writing
`allFiles`. The folder-play scan writes `allFiles` only inside the
`path.length === 0` branch at `Mp3PlayerView.svelte:1221-1225`, and as recorded
under Q35 that branch is not reachable from the only call site (`:2009`), so today
it does not overwrite the index. `beginQueue` setting
`deviceLibrary.trackListLockedByUser = true` (`:1106`) only suppresses the index
scan's queue hydration (`deviceLibrary.svelte.ts:196`); it does not stop the index
scan's `allFiles` writes or its cache write (`:194`, `:197`).

## Q34

Completion is the native `done` flag: `getAudioScanBatch` computes
`done = session.pendingDirs.isEmpty()` and drops the session when true
(`DirectoryReaderPlugin.java:201-204`, returned at `:210`). The JS loop mirrors it
into `scanCompleted` (`folderScan.ts:86`) and resolves with the collected files
(`:101`).

For the index caller, completion is the `.then` at
`deviceLibrary.svelte.ts:192-198`: `view.allFiles` is replaced with the promise
result (`:194`), progress is cleared (`:195`), the queue is hydrated unless the
user locked it (`:196`), and only then is the cache written (`:197`). Tests pin
this order and the lock: `tests/unit/device/deviceLibrary.test.ts:223-246`,
`:261-270`.

On a mid-scan failure none of that runs. `startLibraryScan`'s `.catch`
(`deviceLibrary.svelte.ts:199-201`) only logs. No `saveCachedLibrary` call happens
on that path, so nothing is cached; `hydrateTracksFromLibrary` is not called; and
`view.allFiles` keeps the partial batches already appended one by one at `:178`.
Progress and the promise are cleared in the `finally` at `:202-207`. The
folder-play caller behaves the same way: its `.catch`
(`Mp3PlayerView.svelte:1230-1237`) logs and resolves the start promise `false`,
with no cache write and no `allFiles` assignment. On a failure the native session
is removed server-side by the `finally` cancel in `folderScan.ts:92-98`.

## Q36

Cold start on Android with `musicSettings.nativeTreeUri` set and no usable cache.
`Mp3PlayerView` is mounted unconditionally with `+page.svelte` for both decks
(`src/routes/+page.svelte:206`, `:231-236`; both are always mounted by design,
`:196-205`), so the order below runs once per deck.

1. The mount effect starts (`Mp3PlayerView.svelte:1539`). `isNativeApp` is true
   (`:97`), so `isRestoring = true` (`:1540`). The template renders the RESTORING
   spinner (`:1639-1643`).
2. `librarySource` defaults to `'device'` (`src/lib/stores/settings.svelte.ts:40`),
   so the drive branch (`:1544-1560`) is skipped and the device IIFE runs (`:1562`).
3. `Promise.all` runs `loadHandleFromIDB()` and
   `loadDeviceCachedLibrary(musicSettings.nativeTreeUri || null, musicSettings.lastFolderName)`
   (`:1563-1566`). With an empty cache the latter returns `null`
   (`src/lib/browse/libraryCache.ts:101-108`).
4. `cachedLibrary` is null, so nothing is restored: no `allFiles`, no
   `hydrateTracksFromLibrary`, no `showQueue`, no `browseVersion` bump from
   `:1566-1572`.
5. `isNativeApp && musicSettings.nativeTreeUri` sets `deviceLibrary.nativeTreeUri`,
   nulls `rootDirHandle` and `pendingHandle`, sets `showQueue = true` and bumps
   `browseVersion` (`:1573-1579`).
6. `if (!('showDirectoryPicker' in window) || !handle) return;` (`:1580-1581`) ends
   the effect body on Android, where the File System Access picker is the desktop
   path and `handle` is null there anyway.
7. `finally` clears `isRestoring` (`:1599-1600`), so the spinner is replaced.
8. The `browseVersion` bump re-runs the browse effect
   (`Mp3PlayerView.svelte:785-792`). `allFiles` is empty and `rootDirHandle` is
   null, so `loadBrowseEntries` takes the last native branch
   (`src/lib/browse/browseNavigation.svelte.ts:177-193`): one live
   `DirectoryReader.listEntries` call, folders with `count: 0` (`:184`) and files
   mapped fresh (`:186`).

Nothing starts a scan at mount. `hasFolderLoaded`
(`Mp3PlayerView.svelte:589`) is true because `deviceLibrary.nativeTreeUri !== null`,
so the empty-state prompt at `:1645` is skipped. What the user sees is the browse
list of the real root folder, populated live, with an empty queue, an empty search
index (`:244-274` only reacts to `allFiles`) and no indexing progress bar
(`:1809`). The index stays empty until one of triggers 7, 8 or 9 in Q35 fires, or
until the Local button takes the cache-miss branch (`deviceLibrary.svelte.ts:262`).

## Q37

`rescanCurrentLibraryIndex` deletes before it scans.
`deviceLibrary.svelte.ts:216-221` computes the key with
`getDeviceLibraryCacheKey({ treeUri, folderName })` and awaits
`deleteCachedLibrary(cacheKey)`, then `deleteCachedLibrary(LAST_LIBRARY_CACHE_KEY)`
when the keys differ. Only afterwards does it call
`startLibraryScan(folderName, { resetExistingFiles: true })` if a tree URI or handle
exists (`:223-225`). `startLibraryScan` then clears `view.allFiles` and bumps the
browse version (`:162-165`) and sets `scanProgress` to `{ pct: 0, filesFound: 0 }`
(`:166`). Both deletes are plain IndexedDB record deletes on the `libraries` store
(`src/lib/utils/idb.ts:88-94`); nothing is copied aside first. This sequence is
pinned by `tests/unit/device/deviceLibrary.test.ts:277-302`, which asserts the two
deletes happen before the scan starts and, in the no-tree / no-handle case, that
`libraryScanPromise` stays null while both keys are still deleted (`:290-302`).

If the scan that follows fails, nothing is written back: `saveCachedLibrary` is
called only in the success `.then` (`deviceLibrary.svelte.ts:197`), and the failure
`.catch` (`:199-201`) only logs. IndexedDB is therefore left with no device
library entry at all, while `allFiles` in memory keeps the partial batches
appended at `:178`. If the app is killed instead, the outcome on disk is the same
and already durable: both keys are gone before any batch is requested, and no
partial cache is ever written, so the next cold start behaves exactly as Q36
(unusable cache, no mount scan, live listing).

## Q38

Nothing verifies a restored device cache against the device, and no refresh is
scheduled. Each restore branch only reads and applies:
`deviceLibrary.svelte.ts:257-260` (native, cache hit), `:293-299` (web, cache only),
`:343-347` (new native tree with an existing cache), `:381-386` (new web handle),
`:457-461` (reconnect), plus the mount branch `Mp3PlayerView.svelte:1566-1572` and
the favourite branch `src/lib/drive/driveLibrary.ts:472-477`. None of them calls
`startLibraryScan`, `listEntries` or any list call after the restore; the only
follow-ups are `bumpBrowseVersion` and `hydrateTracksFromLibrary`. There is no
staleness check either: `savedAt` is written at
`src/lib/browse/libraryCache.ts:86` but the only reader in the tree is the Drive
cache TTL at `src/lib/utils/idb.ts:124` (`DRIVE_CACHE_TTL`, `:97`), never the
device library.

The consequence is that a file deleted (or added) while the app was closed stays
in the restored index indefinitely. `allFiles` is the restored list, the browse
list prefers it whenever it is non-empty
(`browseNavigation.svelte.ts:122-145`), and only a rescan (Q35 triggers 8/9), the
first-search scan (trigger 7, which requires `allFiles.length === 0`,
`Mp3PlayerView.svelte:344-347`) or a file op (`src/lib/files/fileOps.ts:209-227`)
can remove it. The Drive path is different and shows the missing half: restoring a
Drive cache does schedule a background refresh of the full listing immediately
after the cached render (`src/lib/drive/driveLibrary.ts:230-250`), replacing
`allFiles` and re-saving the cache at `:248-250`.
