## Q13. Where does a deck's live position live, who writes it, and at what rate?

For live playback the element's `timeupdate` is the origin. `src/lib/audio/player.svelte.ts:463-469`
skips the write while a seek is in flight (`if (seeking !== null) return`, `:464`), skips
it if less than `THROTTLE_MS` has elapsed (`:466`, constant at `:125`), and otherwise
copies `element.currentTime` into `state.currentTime` (`:468`). So the reactive position
updates at most ~4 Hz while a track plays. `seek()`
(`src/lib/audio/player.svelte.ts:653-658`) and the track-change resets
(`:234`, `:412`, `:426`, `:650`) are the only other writers.

From there one effect in the view mirrors it into the engine, unconditionally:
`src/lib/components/views/Mp3PlayerView.svelte:695-707` reads `player.state.currentTime`
and assigns `mediaEngine.deckACurrentTime`/`deckBCurrentTime` (`:699`/`:702`). An earlier
effect in the same view (`:615-689`) also pushes an `untrack()` snapshot of the same
value (`:637`, `:650`) whenever track metadata or the buffering flag changes, and
additionally calls `mediaEngine.updateTime()` for the global field only when this deck is
the visible one and music owns the display (`:673-687`). The fields are declared at
`src/lib/stores/mediaEngine.svelte.ts:135-136` and initialised at `:197-198`.

Readers: `src/lib/components/ui/MiniPlayer.svelte:67-72` derives `deckCurrentTime` from
whichever deck is displayed, and `:80-82` derives the play/pause flag the same way.
Nothing else reads them.

## Q14. Can a position be read for a deck that is not the displayed one, and what does `clear()` do?

Yes. The push at `Mp3PlayerView.svelte:695-707` is not gated on the deck being visible:
it reads `player.state.currentTime` and writes its own deck field regardless. The gate
that exists (`if (isMusicView) claimMusicControls()`, `:668`) covers only the transport
handlers, not the position. So `mediaEngine.deckBCurrentTime` is live while deck A's
sub-tab is showing, which is exactly what the MiniPlayer's deck switch reads
(`MiniPlayer.svelte:68-71`).

`mediaEngine.clear()` (`src/lib/stores/mediaEngine.svelte.ts:339-362`) zeroes both
decks: `deckACurrentTime` and `deckBCurrentTime` at `:355-356`, plus both items,
durations, buffering flags and every `*Playing` flag (`:344-360`).

That zeroing is not durable while a deck is mounted. `clear()` also sets
`this.source = null` (`:354`), and the deck effect reads `mediaEngine.displayedSource`
(`Mp3PlayerView.svelte:616`) and `mediaEngine.source` (`:706`), so the effect re-runs and
immediately writes the deck's live `player.state.currentTime` back over the zero. The
engine field therefore only stays 0 if no deck is mounted or the deck's own time is 0.

## Q15. What are `lastTrackKey` / `lastTrackIndex` / `lastTrackTimestamp`, who writes each, and why is the timestamp forced to 0?

All three sit in the shared `musicSettings` store
(`src/lib/stores/settings.svelte.ts:45-47`); the field comment calls it "seconds, saved
on pause/steal for UX continuity" (quoted verbatim from the source).

`lastTrackIndex` and `lastTrackKey` are written together by the player's
`setCurrentTrack()` (`src/lib/audio/player.svelte.ts:217-220`), which runs on every
selection (queue load, advance, prev, append re-point). Both decks write the same two
fields, so they are last-writer-wins across decks; the view says so and refuses to read
`lastTrackIndex` for its own track (`Mp3PlayerView.svelte:537-541`). `lastTrackKey` is
read back for restore by matching against the sorted list (`:142-150`), with
`lastTrackIndex` as fallback.

`lastTrackTimestamp` is never given a nonzero value anywhere in the repo. Every
assignment is `= 0`: `player.svelte.ts:326` (queue load), `:337` (track start), `:413`
and `:425` (advance, both branches), `:479` (element `pause`), `:482` (`ended`), `:495`
(element `error`), `:649` (`prev`), plus `Mp3PlayerView.svelte:127` and `:135` (the
hydrate paths). `grep -rn lastTrackTimestamp src/ tests/` returns only those writes,
the type declaration (`player.svelte.ts:50`) and the test fixtures.

It is forced to 0 by a view effect whose entire body is that reset:
`Mp3PlayerView.svelte:553-557` watches the field and writes 0 whenever it is nonzero. The
effect has no explanatory comment of its own; it sits directly under the "register
stop-callback for cross-view audio exclusivity" heading (`:552`). The reason is in
git history rather than in the code: commit `77fb0ec` "Refine media playback UI and
persistence" deleted the writer (`musicSettings.lastTrackTimestamp = audioEl.currentTime`
in both the stop callback and `onPause`), changed the restore read
`currentTime = musicSettings.lastTrackTimestamp` into `currentTime = 0`, and added this
reset effect in the same diff. So the field is the tombstone of a removed per-track
resume feature: schema and write sites survive, and two mechanisms guarantee it is
always 0.

## Q16. What is `mp3TrackPositions` and why is it wiped on module load?

It is a `persisted()` store shaped `{ positions: Record<string, number> }` keyed by
track key, declared at `src/lib/stores/settings.svelte.ts:143-145`. Three lines later,
on the same module load, it is emptied if it holds anything:
`if (Object.keys(mp3TrackPositions.positions).length > 0) { mp3TrackPositions.positions = {}; }`
(`:147-149`).

`grep -rn mp3TrackPositions src/ tests/ docs/` returns three hits, all in
`settings.svelte.ts` (the declaration and the two lines of the wipe). There is no reader
and no writer in `src/`, none in `tests/`, and no mention in `docs/`. The mechanism is
dead. It is not `trim`med and has no cap; its only live effect is that booting the app
writes `{"positions":{}}` (16 bytes) back to the `mp3-track-positions` key.

## Q17. What does `player.stop()` do to the position, and what does `resume()` restart from?

`stop()` is exactly two calls, `haltPlayback()` then `unload()`
(`src/lib/audio/player.svelte.ts:588-591`), and it keeps the queue.

`haltPlayback()` (`:231-238`) sets `state.isPlaying = false`, `state.isBuffering = false`,
`state.currentTime = 0` (`:234`), pauses the element and sets `element.currentTime = 0`
(`:237`). `unload()` (`:224-228`) removes the `src` attribute and calls `element.load()`.

So when another source claims audio, the view's registered stop callback
(`Mp3PlayerView.svelte:559-566`, which calls `player.stop()` at `:565`) destroys both
copies of the position: the reactive one and the element's. Nothing survives except the
queue and `currentIndex`.

`resume()` (`player.svelte.ts:593-647`) therefore restarts from zero. With no `src` it
takes the rebuild branch (`:598-606`): it re-selects the current index and calls
`loadAndPlayAt(index, true, true)`, which re-resolves the URL and plays the track from
the beginning. There is no position restore on any path. The only position preservation
in `resume()` is the native-only `src` re-set (`:608-618`), which saves and restores
`element.currentTime` across the reassignment, and that branch is only reached when an
`src` is still loaded, which `stop()` has already removed.

## Q18. What collides with writing a saved position from live playback?

Writing `state.currentTime` is a 4 Hz write (`player.svelte.ts:463-469`). Pumping that
into a `persisted()` store means one flush per tick at best, because `persisted()`
coalesces per microtask, not per second (`src/lib/persisted.svelte.ts:68-75`), and each
flush re-serialises the whole store (`JSON.stringify(trim(state))`, `:47`) and writes
the entire key (`localStorage.setItem`, `:48`). For `music-settings` that blob is the
whole settings object including `favoriteTracks` and `favoriteFolders`: a 500-byte
default (`settings.svelte.ts:33-60`) plus ~345 bytes per native favourite, ~382 per
Drive favourite and ~155 per web favourite (measured). A hundred favourites already
means ~35 KB serialised four times a second.

The codebase has already paid for this lesson once. Podcast progress keeps the position
in memory every tick and commits to the store only every 20 s plus on pause, and the
constant's docstring says why: each flush "serialises the ENTIRE trimmed podcast-data
blob ... and a single over-quota write permanently kills that store"
(`src/lib/podcast/progress.ts:34-49`, used at `src/lib/podcast/podcastPlayer.ts:213-232`
and `:252-256`).

Nothing else in the app writes localStorage from `timeupdate`. The only `timeupdate`
listeners are `player.svelte.ts:463`, `YoutubePanel.svelte:539` and the podcast element
(`podcastPlayer.ts:200-240`). Timer-driven writers are: `mediaEngine`'s 3 s
`MediaControls.updatePosition` and 5 s background watchdog
(`mediaEngine.svelte.ts:918-925`, `:756-775`, both native-only and neither touching
localStorage); the sleep timer's 1 s tick (`sleepTimer.svelte.ts:44-46`), which
re-assigns `sleepTimerSettings.endsAt` to the same value each tick
(`:22-25`) so the source's `===` equality means no notification and no flush; and the
podcast 20 s flush above. Non-timer writers are the tab-change effect
(`+page.svelte:141-143`) and the error recorder (`runtimeDiagnostics.svelte.ts:62-77`).

One trap in the current setup: `musicSettings` passes `debounceMs: 5000`
(`settings.svelte.ts:60`), but the option is deprecated and ignored
(`persisted.svelte.ts:10-11`); writes are immediate (microtask), so a comment or design
that assumes 5 s of slack is wrong.

## Q19. How does `persisted()` work exactly?

Init (`src/lib/persisted.svelte.ts:22-34`): it reads `localStorage.getItem(key)` inside a
`try` (`:26`); if a value parses, `stored = { ...defaults, ...JSON.parse(raw) }`
(`:27-28`), a shallow merge, so new top-level keys added in a later build get their
defaults and unknown legacy keys are kept in the object; on a throw it falls back to
`defaults` (`:29-31`). It then `structuredClone`s the result into `$state` (`:34`) so the
defaults literal is never mutated.

Reactivity (`:78-86`): the effect reads one property per `Object.keys(defaults)` entry
(`:84`) and then calls `scheduleFlush()`. Only keys present in `defaults` at init are
tracked, which is also why a legacy key that only exists in storage can never trigger a
flush.

Write path (`:37-75`): `flushToLocalStorage()` applies `trim` if supplied, serialises,
and calls `setItem` (`:47-48`). The call is deferred to the end of the current microtask
by `scheduleFlush()` (`:68-75`) so several mutations in one event loop produce one write.
`trim` affects only the serialised copy; the in-memory state stays full (that is how
`podcastData` keeps 150 episodes in memory and 120 on disk,
`tests/unit/models/podcast-persist.test.ts:63-96`).

Quota (`:50-56`): the `setItem` is wrapped in `try`/`catch`; a throw is logged once
behind `_writeErrorLogged` and swallowed, so the effect is not torn down. The comment
explains the past failure mode: a quota throw inside the effect made Svelte destroy it,
after which that store silently never persisted again. Regression coverage exists:
`tests/unit/models/podcast-persist.test.ts:102-118` throws one `QuotaExceededError` on the
first write and asserts the second write still lands.

Sync flush on lifecycle (`:88-106`): `pagehide`, `beforeunload`, `visibilitychange`
(when hidden) and the Capacitor `pause` event all call `flushToLocalStorage()` directly.

## Q20. Does an in-place mutation schedule a flush?

No. The store must have the top-level key reassigned. The tracked reads are per
top-level property (`persisted.svelte.ts:84`) and Svelte 5 keeps a source per property
on the proxy object (`node_modules/svelte/src/internal/client/proxy.js:127-150`,
`sources.set(prop, ...)` in the get/set handlers). `state.favoriteTracks.push(x)` writes
the array proxy's own `length`/index sources, and the effect never read those, so it does
not re-run and no flush is scheduled. Reassigning the key writes that property's source
and does.

The code follows the rule everywhere it touches a persisted list.
`toggleFavoriteTrack` and `removeFavoriteTrack` both replace the array
(`src/lib/favorites/favoriteTracks.ts:208`, `:215`); the folder favourites do the same
(`src/lib/drive/folderPicker.svelte.ts:234`, `:245`, `:247`). `grep` for
`favoriteTracks.|favoriteFolders.` followed by `push`/`splice` returns nothing.

Evidence in tests is all positive-case: every persistence test assigns a top-level key
before asserting (`tests/unit/models/podcast-persist.test.ts:13-35`, `:63-96`, `:130-140`;
`tests/unit/favorites/favoriteTracks.test.ts:150-200` only checks in-memory shape). No
test pins the negative case, and `grep -rn persisted tests/unit` finds no test file for
the module itself, so the rule is convention plus Svelte semantics, not a red test.

## Q21. What are all the localStorage keys, what does each weigh, and what is the budget?

Eight keys come from `persisted()` (`src/lib/stores/settings.svelte.ts`), measured at
their default values:

| key | source | default weight | growth |
|---|---|---|---|
| `app-settings` | `settings.svelte.ts:8-18` | 195 B | fixed |
| `sleep-timer-settings` | `:25-28` | 33 B | fixed |
| `music-settings` | `:33-60` | 500 B | `favoriteTracks` ~345 B (native) / ~382 B (drive) / ~155 B (web) each; `favoriteFolders` ~191 B (device, carries a SAF `treeUri`) / ~75 B (drive) each; `browsePath`, `lastTrackKey` |
| `podcast-settings` | `:72-79` | 177 B | fixed |
| `podcast-data` | `:110-114` | 84 B | **dominant**: ~852 B per episode with a 600-char description, capped at 120 per podcast (`:126`), so ~1 MB for ten subscriptions |
| `mp3-track-positions` | `:143-145` | 16 B | wiped on every load (`:147-149`) |
| `weather-settings-v2` | `:162-192` | 497 B | tiny per city |
| `radio-data` | `:196-198` | 16 B | ~300 B per favourite station |

Seven more keys are written directly, outside `persisted()`:

- `google-drive-session`, ~541 B with a real token, scope and user profile
  (`src/lib/stores/googleDriveSession.svelte.ts:15-18`, written at `:45-58`).
- `runtime-diagnostics`, at most 20 entries (`runtimeDiagnostics.svelte.ts:2`, `:62-77`),
  each entry carrying `message`/`stack`/`details`/`userAgent`, so this can reach tens of
  KB after a burst of errors.
- `navigation-state`, tiny (`+page.svelte:28`, `:141-143`).
- `update-offered-version`, a number (`src/lib/utils/androidUpdate.ts:71`, `:100-102`).
- `youtube-audio-save-phase`, one word (`src/lib/youtube/saveMarker.ts:10`, `:21`).
- `google-drive-folder-picker-pending`, the string `'1'`
  (`src/lib/drive/folderPicker.svelte.ts:33`, `:50`).
- `runtime-error-notice-shown` is `sessionStorage`, not localStorage (`+page.svelte:105`).

`src/lib/utils/storage.ts` is a helper for safe reads/writes but has no importers
(`grep -rn "utils/storage" src/ tests/` returns nothing).

Budget ceiling: **unresolved numerically.** No byte figure is documented anywhere. The
only statements are qualitative: "the WebView localStorage quota"
(`persisted.svelte.ts:14-24`) and the podcast data-loss note
(`settings.svelte.ts:113-121`). `grep -rn "quota|5MB|5 MB" docs/` finds no number, and no
code reads `navigator.storage` or measures usage. What is certain from the code is the
failure mode when it is crossed: `setItem` throws `QuotaExceededError`, the write is
swallowed and lost (`persisted.svelte.ts:50-56`), verified by
`tests/unit/models/podcast-persist.test.ts:102-118`.

Fit for a new list store: a pairs list is negligible against `podcast-data`. At roughly
200 bytes a pair (two `getStoredFileKey` strings plus a few numbers), 500 pairs is
~100 KB, which is a tenth of one podcast subscription's trimmed episode window. The
pressure point is not the new key; it is that any per-250 ms write to `music-settings`
re-serialises that 500 B plus the whole favourites list every tick (Q18).

## Q22. How does `musicSettings` migrate legacy fields, and what is the `trim` precedent?

Migration is an in-place patch at module load, with no version field and no deletion
of the old key. The one instance is the legacy single playback speed:
`settings.svelte.ts:62-68` casts the store to read `playbackSpeed`, copies a positive
value into `deckASpeed` and `deckBSpeed`, and leaves the original property alone. It
survives in storage because the init merge keeps unknown keys
(`persisted.svelte.ts:27-28`) and it is untracked, because `Object.keys(defaults)` no
longer contains it (`:84`). The same style of normalisation runs for
`appSettings.listTileTone` at import (`settings.svelte.ts:20`).

So the precedent for a new key is: add it to the `defaults` literal, and if an older
shape has to be read, cast inside a small block at module scope after the `persisted()`
call, then leave the old data where it is. There is no schema-version gate and no
`delete` of migrated keys anywhere in the file.

Size-bounded store precedent: the `trim` hook only, used once. `podcastData` passes
`trim` (`settings.svelte.ts:116-141`) which keeps the full subscription manifest and
caps episodes at `MAX_EPISODES_PER_PODCAST = 120` (`:126`), preferring episodes with
`played`/`progress`/`positionSec` and filling the remainder with the newest
(`:129-136`). `trim` is applied at serialisation only (`persisted.svelte.ts:47`).
`mp3TrackPositions` and `favoriteTracks` have no `trim` and no cap.

## Q23. Is there a precedent for a persisted list of user items?

Yes, two, both unbounded, both keyed rather than indexed.

`musicSettings.favoriteTracks` is `FavoriteTrack[]` (`settings.svelte.ts:58`), a
discriminated union of four row shapes, `web` / `native` (+ `path`) / `drive` (+
`fileId`) / `youtube` (+ `videoId`) (`src/lib/models/music.ts:43-62`). Each row carries
its own `key`, always `getStoredFileKey(file)` (`favoriteTracks.ts:133`), plus denormalised
display fields (`name`, `title`, `artist`, `relativePath`) so the row renders without the
library. `musicSettings.favoriteFolders` is the smaller sibling, an inline type
`{ id; name; source: 'device' | 'drive'; treeUri? }` (`settings.svelte.ts:57`). Neither
list is trimmed or capped; both are replaced wholesale on every change
(`favoriteTracks.ts:208`, `:215`; `folderPicker.svelte.ts:234`, `:245`, `:247`).

Dead references are not pruned. `resolveFavoriteTrackFile`
(`src/lib/favorites/favoriteTracks.ts:165-194`) looks the key up in the loaded library
index first, then in the live queue, and otherwise rebuilds a `StoredAudioFile` from the
row's own metadata for `native` (needs `path`, `:170-179`) and `drive` (needs `fileId`,
`:181-191`). It returns `null` for a `web` row and for a `native` row with no `path` or a
`drive` row with no `fileId` (`:194`). The caller then toasts instead of playing
(`playFavoriteTrack`: "not available in the current library" at `:248`, empty batch at
`:257`). `getResolvedFavoriteTrackFiles` de-duplicates by stored key (`:220-236`).

The net behaviour: a favourite pointing at a deleted file stays in the list forever and
fails politely at play time. The only thing that removes a row is the user toggling it
off. A pairing list would inherit exactly this contract unless a prune is added.

## Q29. How is a `StoredAudioFile` keyed, and what does the key leave out?

`getStoredFileKey` (`src/lib/models/music.ts:135-139`) returns `d:${fileId}` for Drive,
`n:${relativePath}` for native and `w:${relativePath}` for web; `getTrackKey` is an alias
(`:141-143`). The three prefixes keep source families apart.

The key deliberately leaves out the container. Native files carry both `relativePath` and
the absolute `path` (`music.ts:15`), and the key uses only `relativePath`. The SAF tree
URI is not in the key either. Two libraries that both hold `Album/x.mp3` therefore produce
the same `n:Album/x.mp3`. Web files behave the same way, and a web library and a native
library never collide because of the prefix. `src/lib/browse/libraryDelta.ts:16-20`
states the choice and its cost explicitly: identity is `relativePath`, so a rename is one
removal plus one addition.

Consumers act on that key, so a collision is a silent drop rather than an error:
`mergeStoredFiles` dedupes by key when appending (`music.ts:243-256`), the player's
`append()` maps the existing track by key (`player.svelte.ts:553-555`), and favourites
match on it (`favoriteTracks.ts:166-167`, `:198`). The only restore path that tolerates
two libraries is favourites' `path` fallback, which is unreachable when the key already
matched.

## Q30. Per source, what turns a saved reference back into audio after a restart, and what happens when the file is gone?

`resolveTrackUrl` (`Mp3PlayerView.svelte:1014-1061`) is the URL seam for the player.
Web goes through `materializeStoredFile`, which returns `entry.file` directly
(`src/lib/drive/driveLibrary.ts:360-362`), then an object URL (`Mp3PlayerView.svelte:1035`).
Native tries the Capacitor bridge URL first (`Mp3PlayerView.svelte:1024-1031`; the same
fast path exists in `src/lib/audio/fileResolver.ts:62-71`), falling back to a blob read
(`fileResolver.ts:31-56`). Drive needs `fileId` plus a live access token:
`materializeStoredFile` calls `ensureDriveAccessToken` then `downloadGoogleDriveFile`
(`driveLibrary.ts:356-384`).

What each needs after a restart:

- **web**: the live `File`. It comes back only from the IndexedDB library cache
  (`restoreStoredFilesFromCache`, `src/lib/browse/libraryCache.ts:167-181`), because
  `CachedWebLibraryFile` stores the `File` itself (`music.ts:64`). There is no path to
  reconstruct from, so if that cache is gone the track is gone.
- **native**: `path` (not the key). `musicSettings.nativeTreeUri` is what re-establishes
  the scan, and the cached library supplies `path` per file.
- **drive**: `fileId` plus a valid token, and the Drive listing comes from its own IDB
  cache keyed by folder id (`driveLibrary.ts:231`, `:250`, `:282`;
  `src/lib/utils/idb.ts:111-121`). Drive files are deliberately absent from the device
  library cache: `saveCachedLibrary` maps only `web` and `native` rows
  (`libraryCache.ts:87-112`).

When the file is gone: a native bridge URL that 404s surfaces as an element `error`, and
the player retries the same `src` once, then advances
(`player.svelte.ts:493-513`, skip loop at `:430-447`). A resolution failure returns
`null`, which becomes `state.error = 'Unable to load this track.'` in `startCurrent`
(`:335`) or a toast from `resolveTrackUrl`'s `catch` (`Mp3PlayerView.svelte:1058-1061`).
A drive download failure throws with an auth-specific message
(`driveLibrary.ts:367-369`, `fileResolver.ts:73-76`).

## Q31. How do the favourites already solve "a persisted reference that may not be present"?

The module header states the contract as preserved behaviour, per source, including the
`null` results (`src/lib/favorites/favoriteTracks.ts:1-58`, especially `:47-52`).

Resolution is the two-step lookup described in Q23: loaded library index, then the live
queue, then per-source reconstruction from stored metadata (native needs `path`, drive
needs `fileId`), and `null` otherwise (`:165-194`). Web has no reconstruction path at all,
so a web favourite resolves only while its library is loaded with a live `File`.

`playFavoriteTrack` (`:239-270`) handles both dead-reference cases with a toast and no
throw: the single favourite fails to resolve (`:246-250`,
"This favorite track is not available in the current library.") and the whole batch comes
back empty (`:253-259`, "No favorite tracks are currently available."), then
`beginQueue` + `startPlayback` with `preserveOrder` and the favourite's index
(`:262-268`). It is also guarded by the deck's `isChangingTrack` re-entrancy flag and
releases it in `finally` (`:240`, `:270`).

Tests cover the resolver and the flow: `tests/unit/favorites/favoriteTracks.test.ts`
(resolve, key match, corrupt-data guards at `:150-260`) and
`tests/unit/models/play-favorite-flow.test.ts`.

## Q32. A web file carries a live `File`. What does the library cache keep, and is a web library restored without a gesture?

`StoredAudioFile`'s web variant is `{ source: 'web'; name; relativePath; file: File }`
(`src/lib/models/music.ts:15`), so the `File` is the value, not a reference.

The cache keeps the `File` itself: `CachedWebLibraryFile` is the same shape including
`file: File` (`music.ts:64`), `saveCachedLibrary` copies it into the payload
(`src/lib/browse/libraryCache.ts:87-95`) and writes it with `idbPut`
(`:126-128`), so IndexedDB structured-clones the blob. That clone is the only reason a
web library survives a restart at all; nothing in localStorage can hold it, and
`getStoredFileKey` for web is `w:relativePath` (`music.ts:135-139`), a string with no
payload.

Restore on mount happens without a user gesture. The mount `$effect`
(`Mp3PlayerView.svelte:1526-1600`) loads the cached library and calls
`hydrateTracksFromLibrary(allFiles)` unprompted (`:1553-1558`), then triggers a warm
refresh (`:1576`). The gesture requirement applies only to File System Access
permissions: `queryPermission` is safe without a gesture, and a `'prompt'` result parks
the handle in `pendingHandle` for the Reconnect button (`:1590-1593`, comment at
`:1580-1583`). The Drive branch of the same effect silently reuses the persisted token
(`:1529-1548`).

## Q33. Both decks share `librarySource`, `lastFolderName`, `nativeTreeUri` and `driveFolderId`. What does that mean?

It means the last deck to load overwrites the other deck's restore hint. All four live in
the single `musicSettings` store (`src/lib/stores/settings.svelte.ts:40-43`), while the
deck's library state (`deviceLibrary`, `src/lib/device/deviceLibrary.svelte.ts`) is a
per-deck instance. Every native pick writes through to the shared field:
`deviceLibrary.svelte.ts:554-555` (SAF tree chosen), `:599` and `:626` (cleared),
`:653` and `:678` (cleared). `beginQueue` writes `lastFolderName`
(`Mp3PlayerView.svelte:1073-1077`) and so does `appendTracksToQueue` (`:1122`). Drive
writes `librarySource`, `nativeTreeUri = ''` and `lastFolderName = 'Google Drive'` in
`activateDriveLibrary` (`driveLibrary.ts:148-150`), plus `driveFolderId`/`driveFolderName`
in `confirmDriveFolderSelection` (`Mp3PlayerView.svelte:996-1000`) and in
`switchToFavorite` (`driveLibrary.ts:452-464`).

Consequence for a pairing whose A track is native and B track is Drive: there is one
`librarySource` and one `nativeTreeUri` to restore from, and both decks read the same
values on mount (`Mp3PlayerView.svelte:1526-1560`), so after a restart both decks restore
whichever library was loaded last. Per-deck bookkeeping exists (`deviceLibrary`,
`driveSession`, the deck's own `allFiles`), but the persisted hint that survives a
restart is global and single-valued. `musicSettings.lastFolderName` is also reused as a
free-text queue label: `favoriteTracks.ts:264` passes `'Favorite Tracks'` into
`beginQueue`, and `Mp3PlayerView.svelte:1156` passes a browse folder label, both landing
in the same field at `:1075`. It is not a reliable library name.

## Q34. Each deck holds its own Drive session. What does that mean for starting two Drive-sourced tracks at once?

The per-deck part is a cache only. Each deck calls `createDriveSession(...)` at
`Mp3PlayerView.svelte:185`, with the comment at `:183-184` stating the intent: one
instance per deck so two mounted decks never share a token. The durable token is the
shared `googleDriveSession` store, persisted at localStorage key `google-drive-session`
(`src/lib/stores/googleDriveSession.svelte.ts:15`, written by `writeStoredSession`
`:45-58`).

`ensureDriveAccessToken` (`src/lib/drive/driveSession.svelte.ts:66-118`) resolves in
order: the session's own token if it is valid and carries the delete scope (`:60-65`);
then hydration from the shared store (`:72-78`); then a **one-shot** native pending
authorization, `consumePendingGoogleDriveAccessToken` (`:81-93`, implemented at
`src/lib/google-drive.ts:247-263`), which writes the result back into the shared store
(`:87-88`); then, only if `interactive`, a full OAuth request (`:102-118`) which also
writes back (`:110-112`); otherwise `null` (`:97-99`).

For a pairing start where both tracks are on Drive, both decks call
`materializeStoredFile` → `ensureDriveAccessToken`
(`driveLibrary.ts:356-368`). The shared store normally answers both, so one token serves
the two downloads, and two simultaneous `downloadGoogleDriveFile` calls are the real
cost. The gap is token acquisition, not token ownership: if neither deck has a local
token and the app has just returned from native sign-in, both calls can reach
`consumePendingGoogleDriveAccessToken`, which consumes the pending response, so only the
first caller gets it; the second then either hydrates from the shared store (populated by
the first, `:87-88`) or returns `null` when `interactive` is false, which surfaces as
"Your Google Drive session has expired"
(`driveLibrary.ts:367-369`).

**Unresolved:** whether the native bridge re-issues a pending token on demand. The JS side
consumes without a guard (`google-drive.ts:252`), and the Android plugin is not read here,
so the race's worst case cannot be settled from the web code alone.
