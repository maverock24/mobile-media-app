## Q12. What the code assumes about `COLUMN_LAST_MODIFIED`, and where `modifiedAt` is consumed

**Repo evidence**

The only place a provider mtime enters the app is the native scan cursor read, and it
is coerced to a number at the plugin boundary:

- `android/app/src/main/java/com/maverock24/mobilemediaapp/DirectoryReaderPlugin.java:58`
  adds `DocumentsContract.Document.COLUMN_LAST_MODIFIED` to `CHILD_PROJECTION`.
- `DirectoryReaderPlugin.java:181`, `:249`, `:311` read it as
  `cursor.isNull(3) ? 0L : cursor.getLong(3)`. A null becomes `0`, with no comment and
  no separate "unknown" marker.
- `DirectoryReaderPlugin.java:405-414` (`createFileObject`) always puts a primitive
  `long modifiedAt`, so JavaScript never receives null or undefined from the native
  path. Absence and a real epoch-0 timestamp are the same value.

Storage and forwarding, all plain copies:

- `src/lib/browse/libraryCache.ts:76` writes `modifiedAt: file.modifiedAt` into the
  cached native entry; `src/lib/browse/libraryCache.ts:127` restores it.
- `src/lib/models/music.ts:154` (`createStoredNativeAudioFile`) copies `entry.modifiedAt`.
- Types carrying the field: `src/lib/models/music.ts:10` (`StoredAudioFile` native
  variant), `:17`, `:39` (`FavoriteTrack`), `:65` (`CachedNativeLibraryFile`), `:144`
  (`NativeDirectoryFile`), `src/lib/native/directory-reader.ts:9`,
  `src/lib/stores/library.svelte.ts:3` and `:10`.

Value reads (three, all passing it to a `File` constructor, none comparing it):

- `src/lib/audio/fileResolver.ts:82` passes it into `downloadGoogleDriveFile`.
- `src/lib/drive/driveLibrary.ts:376` passes it the same way; `:384` uses it as
  `lastModified: entry.modifiedAt ?? Date.now()` on the materialised `File`.
- `src/lib/google-drive.ts:632` declares the option, `:667` and `:675` apply
  `lastModified: options.modifiedAt ?? Date.now()`.

Copies into and out of the favorites model, no logic:

- `src/lib/favorites/favoriteTracks.ts:146`, `:156` (`toFavorite` native and drive),
  `:177`, `:188` (`resolveFavoriteTrackFile`).

Never compared, never used to decide anything is unchanged:

- `grep -rnE "modifiedAt\s*(===|!==|>=|<=|>|<)" src/ --include=*.ts --include=*.svelte`
  returns zero matches. The only `.modifiedAt` value reads in `src/` are the three
  `lastModified:` sites above (`driveLibrary.ts:384`, `google-drive.ts:667`, `:675`).
- No repository code compares two observations of one file. No pruning, cache
  validation, rescan decision or dedupe reads `modifiedAt`. Identity is
  `relativePath` (`src/lib/models/music.ts:114-117`, `getStoredFileKey`), not mtime.

One write site invents the value rather than reading it: `src/lib/device/deviceLibrary.svelte.ts:570`
sets `modifiedAt: Date.now()` on the native entry created for a Drive file just
downloaded to the phone, then appends it to `view.allFiles` (`:572`).

So the assumption in the code is: `modifiedAt` is an optional display and `File`
metadata field. Nothing treats it as a trustworthy change signal, because nothing
reads it for a decision at all.

## Q13. What the repo records about providers that do not populate mtime, or populate it coarsely

### Repo evidence

The pointers named in the question do not contain what the question expects:

- `docs/device-verification.md:37-51` is section "1. Load a local folder through the
  SAF picker". It lists the expected index bar text, three failure strings, a logcat
  line and the two code entry points. It says nothing about mtime, modified times or
  provider behaviour.
- `docs/device-verification.md:304-319` is section "19. File operations: move, copy,
  delete". It covers delete/move/copy toasts and the `Move on folders is not wired
  yet.` follow-up. It says nothing about mtime.
- `docs/adr/0002-file-move-copy-delete.md` (whole file) sets the SAF file-op scope and
  the Drive scope. It never mentions mtime, `COLUMN_LAST_MODIFIED` or provider
  variance.
- `grep -rniE "mtime|modified|last.?modif|provider|coarse" docs/ --include=*.md`
  (excluding `docs/archive/`) matches only `docs/refactoring-plan.md:441` ("native with
  path/mime/mtime", a field list) and unrelated prose in
  `docs/performance-analysis.md:428`, `:604` about podcast progress cadence.

No comment in the plugin discusses provider variance either:

- `DirectoryReaderPlugin.java:28-38` is the class comment. It explains why
  `DocumentFile` traversal is avoided (one ContentResolver IPC per call) and that one
  child-cursor query returns id, name, mime and mtime. Performance only.
- `DirectoryReaderPlugin.java:167-169` explains why a directory's files are never
  split across batches. `:197` explains skipping an unreadable directory. Nothing
  about null, zero or coarse mtimes. The null handling at `:181`, `:249`, `:311` is a
  bare `? 0L` with no comment.

Test fixtures, checked for a null, zero or unchanged mtime model: none.

- `tests/unit/browse/folderScan.test.ts:44-50` (`nativeFile` helper) omits
  `modifiedAt` entirely. `:288-298` asserts the resulting entry has
  `modifiedAt: undefined`, so the unset case is pinned but never the zero case.
- `tests/unit/browse/libraryCache.test.ts:29-35` (`native` helper) also omits it.
  `:178` and `:191` round-trip `modifiedAt: 7` through the cache. `:217` asserts
  `modifiedAt: undefined` after a save/load of a file without one. `:203` covers an
  empty library.
- No fixture uses `modifiedAt: 0`, no fixture represents two observations of the same
  file with the same timestamp, and no test exercises a scan where a directory's mtime
  is unchanged between runs.

Net repo answer: apart from the `? 0L` coalesce and the fixtures above, the repo
records nothing about providers that return null or coarse mtimes. This half is
`unresolved` as posed: the cited sections do not discuss mtime.

### Platform reference

Official documentation, API reference for the column
(<https://developer.android.com/reference/android/provider/DocumentsContract.Document#COLUMN_LAST_MODIFIED>,
page "DocumentsContract.Document", section heading **COLUMN_LAST_MODIFIED**):

> "Timestamp when a document was last modified, in milliseconds since January 1, 1970
> 00:00:00.0 UTC. This column is required, and may be null if unknown. A
> DocumentsProvider can update this field using events from OnCloseListener or other
> reliable ParcelFileDescriptor transports."

What that text settles, read literally:

- The provider may legally return null for the column ("may be null if unknown"). It is
  required to be present in the projection, not to carry a value.
- Updating the value is discretionary ("can update ... using events from
  OnCloseListener or other reliable ParcelFileDescriptor transports"). The docs state
  no freshness obligation and no granularity, so a coarse or stale value is legal.

Same page, section heading **DocumentsContract.Document** (class description):

> "All columns are read-only to client applications."

A second official source fixes the unknown sentinel:
<https://developer.android.com/reference/androidx/documentfile/provider/DocumentFile#lastModified()>,
page "DocumentFile", section heading **lastModified()**:

> "Returns the time when this file was last modified, measured in milliseconds since
> January 1st, 1970, midnight. Returns 0 if the file does not exist, or if the
> modified time is unknown."

That matches the plugin's `? 0L` at `DirectoryReaderPlugin.java:181`.

**Directory mtime: unresolved from the Android documentation.** No Android doc states
that a directory's `COLUMN_LAST_MODIFIED` changes when its direct children change, or
that it changes for deeper changes. Pages checked, all with no occurrence of
"modified" or `COLUMN_LAST_MODIFIED` except where noted:

- <https://developer.android.com/guide/topics/providers/document-provider> ("Open
  files using the Storage Access Framework"): no mention of modified times at all.
- <https://developer.android.com/training/data-storage/shared/documents-files>
  ("Access documents and other files from shared storage"): no mention of modified
  times at all.
- <https://developer.android.com/reference/android/provider/DocumentsProvider>: the
  column appears only for recents ordering, `queryRecentDocuments`, "The returned
  documents should be sorted by Document.COLUMN_LAST_MODIFIED in descending order of
  the most recently modified documents."
- The one directory-specific statement on the `DocumentsContract.Document` page is
  section heading **FLAG_DIR_PREFERS_LAST_MODIFIED**: "Flag indicating that a
  directory prefers its contents be sorted by COLUMN_LAST_MODIFIED. Only valid when
  COLUMN_MIME_TYPE is MIME_TYPE_DIR." That is sort order, not change propagation.

The nearest primary source for the semantics a filesystem-backed provider inherits is
POSIX.1-2017, not Android. <https://pubs.opengroup.org/onlinepubs/9699919799/functions/unlink.html>,
page "unlink, unlinkat - remove a directory entry", DESCRIPTION:

> "Upon successful completion, unlink() shall mark for update the last data
> modification and last file status change timestamps of the parent directory."

and <https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/V1_chap04.html#tag_04_09>,
page "General Concepts", section heading **4.9 File Times Update**:

> "An implementation may update timestamps that are marked for update immediately, or
> it may update such timestamps periodically. At the point in time when an update
> occurs, any marked timestamps shall be set to the current time and the update marks
> shall be cleared."

Read together: only the immediate parent directory's timestamp is marked, so a change
one level deeper does not touch a grandparent; and even the marked update may land
late. Android imposes no additional requirement on top of that, so for the platform
half the honest answer stays `unresolved` for "does a directory's mtime track its
children", with the POSIX rule as the only documented behaviour a provider is likely
to inherit. No Android doc quoted above says a provider is backed by a POSIX
filesystem.

## Q14. What else could identify an unchanged directory today

**Repo evidence**

For a file, one provider-assigned value survives to disk: the document URI, which is
built from the document id and stored in `path`.

- `DirectoryReaderPlugin.java:191-193` (`getAudioScanBatch`), `:264-265`
  (`listEntries`), `:321-322` (`listAudioFiles`) build the child URI with
  `DocumentsContract.buildDocumentUriUsingTree(treeUri, docId)` and pass
  `docUri.toString()` into `createFileObject`, which stores it as `path` at `:409`.
- `DirectoryReaderPlugin.java:178` reads `COLUMN_DOCUMENT_ID` from the cursor; `:55`
  keeps it in the projection. It is never returned as its own field.
- The TS side types `path: string` at `src/lib/native/directory-reader.ts:6`, and it is
  persisted: `src/lib/models/music.ts:63` (`CachedNativeLibraryFile.path`) and
  `src/lib/browse/libraryCache.ts:74` (`path: file.path`).

For a directory, nothing provider-assigned crosses the bridge:

- The folder object built at `DirectoryReaderPlugin.java:255-257` carries only
  `kind`, `name`, `relativePath`. No document id, no mtime, no child count.
- `src/lib/native/directory-reader.ts:12-16` (`NativeDirectoryFolder`) mirrors exactly
  those three fields.
- `DirectoryReaderPlugin.java:345-385` (`resolveDocumentId`) recomputes a directory's
  id on every call: the root comes from `DocumentsContract.getTreeDocumentId(treeUri)`
  at `:346`, and each path segment costs one child-cursor query that matches on display
  name and directory mime (`:357-376`). The id is a local variable, returned at `:384`,
  and never reported to JavaScript.
- Nothing directory-shaped is persisted: `CachedLibrary` is
  `{ folderName, files, savedAt, cacheKey? }` (`src/lib/models/music.ts:68`) and
  `saveCachedLibrary` maps files only (`src/lib/browse/libraryCache.ts:60-82`).

So today: a file's document URI in `path` is the only value stable across restarts
that also survives to the cache, and it is name-independent. `relativePath` is
name-based, so it changes on rename. Directories have no such value anywhere, in
memory or on disk.

**Platform reference (context only)**: the document id is the stable handle a provider
offers. <https://developer.android.com/reference/android/provider/DocumentsProvider>,
page "DocumentsProvider", class description: "Each document under a provider is
uniquely referenced by its Document.COLUMN_DOCUMENT_ID, which must not change once
returned."

## Q15. What the app does today when a scan cannot proceed at all

**Repo evidence**

The native failure that matters here is a missing session, plus an unreachable start
directory:

- `DirectoryReaderPlugin.java:154` rejects `getAudioScanBatch` with "Audio scan session
  not found." The session is removed when the queue drains (`:201-204`) or when
  `cancelAudioScan` runs.
- `DirectoryReaderPlugin.java:118-122` rejects `startAudioScan` with "Selected
  directory is not accessible." (reject at `:120`) when `resolveDocumentId` returns
  null.
- Per-directory read failures do not reject; they are swallowed at `:196-198` and the
  walk continues.

On the JavaScript side a reject simply propagates:

- `src/lib/browse/folderScan.ts:91-99` is the `finally`: it cancels the session if the
  scan did not complete and rethrows the original error, since the function has no
  `catch` and no fallback listing.
- `src/lib/device/deviceLibrary.svelte.ts:199-201` catches it and does
  `console.error('Failed to scan selected library.', error)` only. No toast, no alert,
  no store write. `:202-207` then clears `libraryScanPromise` and `scanProgress`.
- `view.allFiles` keeps the partial batches already appended at `:178`, because the
  replaced value (`:194`) and the cache write (`:197`) live in the resolved branch
  that never runs.
- `startLibraryScan` is `void` (`:161`); the rejecting promise is stored in
  `libraryScanPromise` (`:190`) and can surface to anyone who awaits it, e.g.
  `src/lib/browse/folderScan.ts:139` inside `collectAllFromPath`.

A failed rescan additionally leaves no cache: `rescanCurrentLibraryIndex` deletes both
cache keys first (`src/lib/device/deviceLibrary.svelte.ts:217-221`) and then starts the
scan (`:223-225`), so the `.then` that would rewrite the cache never runs.

Folder-playback scans report failure only in the console:
`src/lib/components/views/Mp3PlayerView.svelte:1230-1236` logs "Failed to scan folder
for playback." and resolves `startFirstPlayableTrack` to false. No toast.

The restore and reconnect paths fail silently:

- `src/lib/device/deviceLibrary.svelte.ts:301-303` catches every error in
  `restoreLocalLibrary` with an empty body and falls through to `return false`, so
  `openLocalSourceButton` (`:233-237`) proceeds to `openFolder`. The user-visible
  messages there are the `alert` at `:325` ("No MP3 files were found in the selected
  folder.") and `:359` ("Unable to open a folder on this device. Please try again."),
  plus the `console.warn` at `:341` for a permission that would not persist.
- `src/lib/device/deviceLibrary.svelte.ts:441-464` (`reconnectFolder`) clears
  `view.allFiles` at `:451` and, if the cached library is missing or empty, starts no
  scan at all; the `catch` at `:463` is empty with the comment `/* user denied */`.

What reaches the user on a scan failure: nothing but a stalled or partially populated
list, with the error only in the console. What reaches `allFiles`: whatever batches
landed before the failure, never pruned, and not written to the cache.

## Unresolved

1. **Directory mtime propagation (Q13 platform half).** No Android documentation states
   whether a directory's `COLUMN_LAST_MODIFIED` changes when its direct children change
   or when something deeper in the subtree changes. The only documented contract is the
   column's own definition, its permission to be null, and its optional update. POSIX
   marks only the immediate parent, and even that may be deferred, but no Android doc
   requires a provider to be backed by a POSIX filesystem.
2. **Q13 repo half as posed.** `docs/device-verification.md:37-51` and `:304-319` do not
   discuss mtime or provider variance, and `docs/adr/0002-file-move-copy-delete.md`
   never mentions mtime. The repo records no note about providers that omit or coarsen
   the value. The only traces are the `? 0L` coalesce and the fixtures listed above.
3. **Granularity a real provider returns.** Not determinable from the repo: no Java
   test, no provider fixture, and no recorded device observation of the column.
