# Research: library-delta, section 3 (the cache: what it holds and how old entries are read)

Branch `main`, commit `1c4347e`. Read-only. Every claim below was re-checked against
the tree; pointers are `path:line`. Unrelated uncommitted edits exist
(`ScreenDimPlugin.java`, `src/lib/native/screen-dim.ts`, `src/routes/+layout.svelte`)
and were not touched.

## Q16

Per file, two shapes. `CachedWebLibraryFile` = `source`, `name`, `relativePath`,
`file` (`src/lib/models/music.ts:58`). `CachedNativeLibraryFile` = `source`, `name`,
`relativePath`, `path`, optional `mimeType`, optional `modifiedAt`
(`src/lib/models/music.ts:59-66`). Per library, `CachedLibrary` = `folderName`,
`files`, `savedAt`, optional `cacheKey` (`src/lib/models/music.ts:68`).

The write mapping in `saveCachedLibrary` copies exactly those fields: web entries are
rebuilt at `src/lib/browse/libraryCache.ts:59-67` (the `File` object is kept as is),
native entries at `:69-76`, and `drive` entries fall through both branches and are
dropped (`:58-81`, pinned by `tests/unit/browse/libraryCache.test.ts:240-244`).

There is no scan-completion flag, no directory or folder record, no tree URI field
(the URI appears only inside the key string, `src/lib/browse/libraryCache.ts:42`) and
no schema version. The `cacheKey` field that is written at
`src/lib/browse/libraryCache.ts:86` is never read anywhere in `src/` or `tests/`
(grep for `.cacheKey` returns no reads; the fixture at
`tests/unit/browse/libraryCache.test.ts:175` only sets it).

## Q17

Key derivation, `getDeviceLibraryCacheKey` (`src/lib/browse/libraryCache.ts:41-45`):
`device:<treeUri>` when a tree URI is passed, else `device-folder:<folderName>`, else
the constant `LAST_LIBRARY_CACHE_KEY = 'last-library'` (`:35`).

`saveCachedLibrary` writes the payload under the derived key
(`src/lib/browse/libraryCache.ts:87`) and then, unless that key already is
`last-library`, writes the same object under `last-library` (`:88-90`). The mirror is
last-write-wins across every library that is ever saved.

`loadDeviceCachedLibrary` (`src/lib/browse/libraryCache.ts:101-108`) reads the exact
derived key first and returns it if present, so the specific key is authoritative. The
mirror is consulted only after a miss on the exact key, and only when its `folderName`
equals the requested one (`:106-107`); otherwise null. Storage primitives:
`loadCachedLibrary` at `src/lib/utils/idb.ts:77-86`, `deleteCachedLibrary` at `:88-94`,
`openIDB` at `:43-56`.

## Q18

`loadCachedLibrary` (`src/lib/utils/idb.ts:77-86`) does a plain object-store `get` and
casts the result to `CachedLibrary` (`src/lib/utils/idb.ts:80`). No version check, no
migration, no defensive parse; the only guard is the `catch` that returns null
(`:83-85`). `openIDB` (`:43-56`) opens database `music-app` at version 2 and creates
the `handles` and `libraries` stores only when absent (`:46-50`); both are created
without a `keyPath` (`:48-49`), so keys are out-of-line strings and values are
unconstrained. No field in the payload records a schema version
(`src/lib/models/music.ts:68`).

Missing-field behaviour, read from the call sites rather than guarded:
- `files` absent makes `cachedLibrary.files.length` throw at the first branch:
  `src/lib/components/views/Mp3PlayerView.svelte:1566` (swallowed by the empty `catch`
  at `:1597`), `src/lib/device/deviceLibrary.svelte.ts:257` (inside the `try` opened at
  `:245`, caught at `:301`), and `src/lib/drive/driveLibrary.ts:473` (inside a
  `try`/`finally` with no `catch`, `:449`/`:480`).
- a native entry without `path` is rehydrated with `path: undefined`
  (`src/lib/browse/libraryCache.ts:125`) and handed to `Capacitor.convertFileSrc(file.path)`
  at `src/lib/audio/fileResolver.ts:63` without a check.
- an unrecognised `source` value falls into the native branch and is relabelled
  `source: 'native'` (`src/lib/browse/libraryCache.ts:117-130`).
- `savedAt` is never read for this cache (Q19). `folderName` is read for the mirror
  match (`src/lib/browse/libraryCache.ts:107`) and for the deck label
  (`src/lib/components/views/Mp3PlayerView.svelte:1568`).

## Q19

`savedAt` is written at `src/lib/browse/libraryCache.ts:86` and typed at
`src/lib/models/music.ts:68`. The only reader in the tree is the Drive cache TTL:
`src/lib/utils/idb.ts:122-124` against `DRIVE_CACHE_TTL` (`:97`). Nothing compares a
device cache's age, so a device library entry never expires; `loadDeviceCachedLibrary`
(`src/lib/browse/libraryCache.ts:101-108`) returns whatever is stored regardless of
`savedAt`. The field appears in tests only as fixture data
(`tests/unit/browse/libraryCache.test.ts:175`, `:203`,
`tests/unit/utils/idb.test.ts:78`).

## Q20

Five writers, all through `saveCachedLibrary`:

- `src/lib/device/deviceLibrary.svelte.ts:197`, at scan completion: the full result of
  `scanNativeAudioFiles` for the Android tree, or `collectStoredFilesFromDirHandle` for
  a web handle (`:170-173`), saved under `s.nativeTreeUri` plus the caller's
  `folderName`. Full listing.
- `src/lib/device/deviceLibrary.svelte.ts:407` (`webkitdirectory` input): only the
  picked files, with `s.nativeTreeUri` nulled just before (`:399`), so the key is
  `device-folder:<lastFolderName or 'Selected Files'>`. A different key family from the
  tree-URI entry, and the content is a selection rather than a tree scan.
- `src/lib/device/deviceLibrary.svelte.ts:434` (native `<input multiple>`): same shape,
  folder name hardcoded to `'Selected Files'`, `s.nativeTreeUri` null (`:419-421`).
- `src/lib/components/views/Mp3PlayerView.svelte:1224` (root folder-play scan): guarded
  by `path.length === 0 && collectedFiles.length > 0` (`:1221-1223`), writes the root
  scan's full list under `device:<treeUri>` with `folderLabel`.
- `src/lib/files/fileOps.ts:219`: `remaining`, the in-memory index minus the deleted
  file, with no rescan. This is the only partial rewrite, and when `remaining` is empty
  it deletes both keys instead (`:224-226`).

`rescanCurrentLibraryIndex` (`src/lib/device/deviceLibrary.svelte.ts:217-221`) deletes
the derived key and the mirror before calling `startLibraryScan`; it is not a writer.

## Q21

`saveCachedLibrary` returns before opening IndexedDB when the mapped list is empty
(`src/lib/browse/libraryCache.ts:83`; pinned by
`tests/unit/browse/libraryCache.test.ts:234-238`). An empty result is therefore never
written, and the previous entry stays untouched.

Only two places remove it: `rescanCurrentLibraryIndex` deletes the derived key and then
`last-library` before the scan starts (`src/lib/device/deviceLibrary.svelte.ts:218-221`),
and `forgetDeletedFile` does the same when the index empties
(`src/lib/files/fileOps.ts:224-226`).

So a scan that yields nothing leaves the old cache in place on both write paths: the
index scan at `src/lib/device/deviceLibrary.svelte.ts:197` (empty `scannedFiles`) and
the folder-play scan at `src/lib/components/views/Mp3PlayerView.svelte:1222-1224`. A
stale listing can outlive an emptied folder until a rescan or a delete-rewrite runs.

Empty-cache branches: on the Android restore path an empty cache starts a scan
(`src/lib/device/deviceLibrary.svelte.ts:257-263`); the tree-URI picker branch
(`:343-347`) and the web handle branch (`:382-386`) leave `allFiles` empty and start
nothing.

## Q22

`idbPut` takes `value: unknown` and calls `put(value, key)`
(`src/lib/utils/idb.ts:24-31`) into a store created without a `keyPath`
(`src/lib/utils/idb.ts:48-49`), so no shape is rejected on write.

IndexedDB stores values with the structured clone algorithm. MDN lists `File` and
`Blob` among the supported types and `Object` for "plain objects (e.g., from object
literals)", and states the clone "clones by recursing through the input object" while
property descriptors and the prototype chain are not duplicated
(https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm).
Reading that against this payload: every stored value is a plain object whose values
are primitives, further plain objects, and `File` objects, all of them supported, so a
round trip preserves both unknown extra fields and the `File` the web branch stores
(`src/lib/browse/libraryCache.ts:63`). MDN does not phrase "unknown fields survive"
verbatim; it follows from plain-object recursion plus the absence of any rejection
case for extra keys.

Nothing rejects an unexpected key: readers only access named properties
(`src/lib/browse/libraryCache.ts:102-107`, `:116-130`), and there is no
`Object.keys`/`JSON.parse`/schema check anywhere in the cache path (grep found none in
`libraryCache.ts`, `idb.ts` or `deviceLibrary.svelte.ts`).

Narrowing happens at the two mapping boundaries rather than in storage:
`saveCachedLibrary` rebuilds each entry from an explicit field list
(`src/lib/browse/libraryCache.ts:58-81`) and `restoreStoredFilesFromCache` builds a
fresh `StoredAudioFile` from named fields (`:115-130`). A new field added to
`CachedLibraryFile` therefore survives IndexedDB but is dropped unless both mappings
are extended. Existing tests push only native and drive entries through IndexedDB
(`tests/unit/browse/libraryCache.test.ts:213-255`); no test round-trips a web entry
with its `File`.

## Q23

`deleteCachedLibrary` (`src/lib/utils/idb.ts:88-94`) is a single unconditional
`idbDelete` (`:33-41`) on one key. No backup copy, no tombstone, no version history, and
no restore path, so deletion is not reversible from the app.

Callers: `rescanCurrentLibraryIndex` deletes the derived key and the mirror
(`src/lib/device/deviceLibrary.svelte.ts:218-221`) before calling `startLibraryScan`, and
`forgetDeletedFile` deletes both keys when the index empties
(`src/lib/files/fileOps.ts:224-226`).

If the delete lands and the following scan never completes, the persisted file list is
gone. Nothing else persists it: `musicSettings` stores only `nativeTreeUri`,
`lastFolderName` and `favoriteFolders` (`src/lib/stores/settings.svelte.ts:41-42`,
`:57`), and Android remembers the tree permission separately
(`src/lib/device/deviceLibrary.svelte.ts:339`), so access survives while the index does
not. On the next cold start nothing is restored and no scan is started
(`src/lib/components/views/Mp3PlayerView.svelte:1564-1575`); the index stays empty
until the user opens the source, where the else branch at
`src/lib/device/deviceLibrary.svelte.ts:261-263` finally starts a scan.
