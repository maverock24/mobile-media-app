# Research: library-delta, section 1 (native scan protocol)

Stage: R (Research). Scope: Q1 to Q11 only. Read-only; branch `main` with unrelated
in-flight edits under `android/.../ScreenDimPlugin.java`, `src/lib/native/screen-dim.ts`
and `src/routes/+layout.svelte`, none of which touch this section.

Java paths are shortened: `DirectoryReaderPlugin.java` =
`android/app/src/main/java/com/maverock24/mobilemediaapp/DirectoryReaderPlugin.java`.

Line numbers below were re-checked against the working tree. A few differ from the
pointers in `questions.md` (for example the extension table is at `:44`, not `:38`);
the numbers used here are the tree's.

## Q1

One batch is a resolved `JSObject` carrying exactly four fields: `files`,
`foldersScanned`, `foldersQueued`, `done` (`DirectoryReaderPlugin.java:206-211`), mirrored
in TypeScript by `AudioScanBatchResult` (`src/lib/native/directory-reader.ts:37-41`). The
unit of work is the directory, not the file: the loop dequeues whole directories and stops
only when the emitted file count reaches `batchSize` or the queue empties
(`DirectoryReaderPlugin.java:167-170`), which is why one directory's files are never split
across batches (`:167-169`).

`batchSize` is per call from JS with a native default of 250 (`:41`, `:158-161`);
`filesAdded` is a local per-batch counter that is never returned (`:165`, `:194`).
`foldersScanned` is a session field (`:76`) incremented once per dequeued directory
(`:172`) and reported cumulatively on every batch (`:208`). `foldersQueued` is a
per-batch snapshot of the queue length (`:209`), so it is not cumulative. On the JS side
`ScanBatchState` adds `totalFiles` (`src/lib/browse/folderScan.ts:33-38`), which is the
client-side running length of `collectedFiles` (`:61`, `:78`, `:83`).

## Q2

No directory-level fact crosses the bridge. The only folder object the plugin builds
carries `kind`, `name` and `relativePath` and nothing else
(`DirectoryReaderPlugin.java:254-258`), matching `NativeDirectoryFolder`
(`src/lib/native/directory-reader.ts:12-16`). There is no directory mtime, no child count,
and no `documentId` field in any payload.

`COLUMN_DOCUMENT_ID` is read at `:178`, `:246` and `:308` but used only to queue a child
directory in Java (`:185`, `:315`, held in `DirNode` at `:63`) or to build a document URI
(`:191`, `:264`, `:321`). The document id is therefore reachable from JS only as part of
the emitted `path` string, which is produced by
`DocumentsContract.buildDocumentUriUsingTree(treeUri, docId)` (`:191`, `:409`) and stored
verbatim (`:405-414`). The URI layout itself is platform-defined and is not asserted
anywhere in this repo; tests use an opaque literal (`tests/unit/files/fileOps.test.ts:71`).

## Q3

The scan root's mtime is never queried. `startAudioScan` resolves the root document id
(`DirectoryReaderPlugin.java:118`) and then calls `queryDisplayName` (`:124`), which
projects `COLUMN_DISPLAY_NAME` only (`:390-391`); nothing else is read for the root.

A child directory's mtime is present in its parent's cursor row (`:181`, `:249`, `:311`)
but is discarded, because a queued directory is represented by a `DirNode` holding only
`documentId` and `relativePath` (`:62-69`), created at `:185` and `:315`. So a directory's
mtime is observable at the moment its parent is read and at no other time, and never
before descending into it. `queryDisplayName` is the only per-document query in the plugin
(`:388-399`).

## Q4

An unreadable directory is silent in three places. A null cursor short-circuits the loop
body with `continue` (`DirectoryReaderPlugin.java:176`), an exception is swallowed
(`:196-198`, comment `:197`), and `foldersScanned` is incremented before the query runs
(`:172`), so a directory that threw is counted exactly like a directory with no children.

A resolved batch has no error field at all (`:206-211`), so "empty" and "failed" are
indistinguishable to the caller. The only rejections in the scan path are a missing
`scanId` (`:148`), an unknown session (`:154`) and the failures inside `startAudioScan`
(`:112`, `:120`, `:139-141`).

## Q5

No. `COLUMN_SIZE` appears nowhere under `android/app/src/main/java/`, and
`CHILD_PROJECTION` lists only id, display name, MIME type and last modified
(`DirectoryReaderPlugin.java:54-59`). `createFileObject` emits six fields and no size
(`:405-414`). Every TypeScript mirror lacks it too: `NativeDirectoryFile`
(`src/lib/native/directory-reader.ts:3-10` and `src/lib/models/music.ts:138-145`), the
native variant of `StoredAudioFile` (`src/lib/models/music.ts:10`), and
`CachedNativeLibraryFile` (`src/lib/models/music.ts:59-66`). The cache write repeats the
same field set (`src/lib/browse/libraryCache.ts:70-77`). `sizeBytes` exists only on the
Drive shapes (`src/lib/models/music.ts:18`, `:40`, `:176`).

## Q6

`cursor.isNull(3) ? 0L : cursor.getLong(3)` (`DirectoryReaderPlugin.java:181`, repeated at
`:249` and `:311`) turns an absent mtime into `0`, and `0` is then passed through
unchanged by `createStoredNativeAudioFile` (`src/lib/models/music.ts:154`), written as
`modifiedAt` (`src/lib/browse/libraryCache.ts:76`) and restored as `modifiedAt`
(`:127`).

The type is `modifiedAt?: number` (`src/lib/models/music.ts:10`), so `0` is a legal
timestamp value and no consumer, type or cache field carries the information that it meant
"absent". The null/none distinction is destroyed at the source and cannot be recovered
downstream.

## Q7

The walk is breadth first. Children are appended with `addLast` (`:185`) onto the
`ArrayDeque` declared at `:73`, and batches dequeue with `removeFirst` (`:171`), so it is
FIFO from the root. `listAudioFiles` has the same shape without batching (`:299-328`).

A batch can contain files from many directories, since the loop iterates directories until
the file budget is met (`:170-199`). It can also contain zero files while `done` is false,
because an empty or failed directory adds nothing (see Q4). `done` is `pendingDirs.isEmpty()`
and nothing else (`:201`), and once true the session is removed (`:202-204`), so a later
batch call for the same id rejects (`:152-155`).

## Q8

The protocol reports presence only. The whole plugin contains no tombstone, `deleted`,
diff or unchanged flag; the single occurrence of the idea is the comment at `:197` about
removed media. The only evidence a caller has that a file is gone is the absence of its
`relativePath` and `path` from a listing that reached `done: true` (`:201`, `:210`).

Because failures are silent (Q4), absence in a completed batch cannot be distinguished
from a directory that was skipped.

## Q9

There is no way to start from a document id. Every plugin method takes `treeUri` plus an
optional `/`-separated name `path` (`:110-118`), and no method accepts a document id
(method list at `:86`, `:108`, `:145`, `:215`, `:224`, `:281`, `:417`, `:499`, `:634`,
`:647`, `:665`, `:684`). An empty path returns the tree's own document id without any
query (`:346-349`).

`resolveDocumentId` costs one full child-list query per segment (`:351-361`), matching by
exact display name and `MIME_TYPE_DIR` (`:367-371`) with no sort order (`:361`,
all-null arguments), and the first match wins because it breaks (`:370`). Starting at an
N-deep path therefore costs N child queries plus one `queryDisplayName` for the start
directory (`:124`). A repeated name resolves to whichever row the provider returns first,
with no ambiguity signal. A renamed or missing segment returns null, as does any exception
during the query (`:374-380`), and both surface as the same rejection, "Selected directory
is not accessible" (`:119-122`).

## Q10

The three listing paths differ in cost and shape.

`listEntries` (`:224-279`) reads one directory with one child query (`:243`) plus one
`queryDisplayName` (`:270`) and returns files with mtime (`:249`, `:265`) and folders with
three fields and no mtime (`:254-258`). `listAudioFiles` (`:281-338`) walks the whole
subtree in one resolved call with no cap and no truncation; the TypeScript
`truncated` and `count` fields (`src/lib/native/directory-reader.ts:26-27`) are never set
by Java. `startAudioScan` plus `getAudioScanBatch` (`:108-212`) is the streaming variant
described in Q1 and Q7.

Callers: `listEntries` at `src/lib/browse/browseNavigation.svelte.ts:129` (live listing
while a scan runs) and `:177` (no index), at `src/lib/browse/folderScan.ts:110` and
`src/lib/components/views/SettingsView.svelte:141` (the native folder picker);
`listAudioFiles` at `src/lib/browse/folderScan.ts:145` (`collectAllFromPath` native
fallback); the streaming scan at `src/lib/browse/folderScan.ts:67`, used from
`src/lib/device/deviceLibrary.svelte.ts:176` (index scan, batch 500 at `:56`) and
`src/lib/components/views/Mp3PlayerView.svelte:1172` (folder playback, batch 48 at
`:108`).

None of the three returns a folder mtime: `listAudioFiles` and the scan emit no folder
objects at all, and `listEntries` emits folders without one (`:254-258`). `listEntries`
and `listAudioFiles` keep no session state, since `AUDIO_SCAN_SESSIONS` is touched only at
`:42`, `:131`, `:152`, `:203` and `:218`, so either can run while a session drains, and
`browseNavigation.svelte.ts:129` already does exactly that.

## Q11

The set is duplicated with two different encodings and no shared source. Java holds a
dotted array, `{ ".mp3", ".m4a" }` (`DirectoryReaderPlugin.java:44`), and tests with
`name.toLowerCase().endsWith(ext)` (`:46-51`). TypeScript holds a dotless array,
`['mp3', 'm4a']` (`src/lib/models/music.ts:85`), and builds a case-insensitive regex from
it (`:87-90`, test at `:93-95`). The two lists agree today by coincidence of content, not
by construction.

On the native path Java is authoritative: it filters before anything crosses the bridge in
all three read paths (`:189`, `:262`, `:319`), so a file whose name it rejects is invisible
to JS no matter what the TypeScript predicate would say. TypeScript's filter applies to the
inputs Java never sees: the web file input (`src/lib/device/deviceLibrary.svelte.ts:395`),
the native file input (`:414`), File System Access walks
(`src/lib/browse/libraryCache.ts:154`, `:173`, `src/lib/browse/browseNavigation.svelte.ts:165`,
`:169`) and Drive (`src/lib/google-drive.ts:490-493`).

TypeScript also has a MIME-based accept path, `isSupportedAudioMime`
(`src/lib/models/music.ts:101-112`), which accepts any `audio/*`. It is used for Drive
(`src/lib/google-drive.ts:493`) and for the native file input
(`src/lib/device/deviceLibrary.svelte.ts:414`), but native scan output can never reach it:
an audio file with no extension or an unsupported one is dropped at
`DirectoryReaderPlugin.java:189` first.
