# A/B pairings: Research 1

Areas: A (Deck ownership and control, Q1–Q7), B (Looping, Q8–Q12), G (Audio
exclusivity, Q35–Q37). Fifteen questions. Read-only; no code was changed.

## Q1

`Player` is a 12-member interface at `src/lib/audio/player.svelte.ts:101-123`:
`state` (:102), `play` (:103), `load` (:105), `append` (:107), `clear` (:109),
`stop` (:111), `pause` (:112), `resume` (:113), `next` (:117), `prev` (:120),
`seek` (:121), `destroy` (:122). The implementation is one returned object
literal, `:528-666`, built by `createPlayer` (:127). A deck is
`Mp3PlayerView`, taking two props (`deck`, `activeTab`) at
`src/lib/components/views/Mp3PlayerView.svelte:103`, and holding one instance in
a `const player` at `:349-366`. No method is callable from outside the owning
view today, because the instance never leaves that scope (see Q2). Five
behaviours are reachable indirectly, all through the engine: `pause()` via
`pausePlayback` (`:1326-1333`), `resume()` via `resumePlayback` (`:1339-1368`),
`seek()` via `handleSeekSeconds` (`:1431-1432`), `next()`/`prev()` via
`skipNext`/`skipPrev` (`:1417-1429`), and `stop()` via the registered
audio-source stop callback (`:559-567`). Nothing reaches `play`, `load`,
`append`, `clear` or `destroy` from outside.

## Q2

No. `const player = createPlayer(...)` at `Mp3PlayerView.svelte:349` is a
component-local `const`; the only exports from `src/lib/audio/player.svelte.ts`
are `createPlayer` (:127) and the types `Player`/`PlayerState`/`PlayerTrack`
(:25, :36, :101). A grep of all of `src/lib` for a `Player`-typed module
variable returns only those declarations, and neither deck instance is bound
with `bind:this` in `src/routes/+page.svelte` (the two mounts are bare
`<Mp3PlayerView deck="A" … />` and `deck="B"`). There is no player registry,
context or store.

## Q3

`registerMusicPlayerView` keeps a `Set` of handlers and returns an unregister
function (`src/lib/stores/musicView.svelte.ts:17-23`); `requestMusicPlayerView`
calls every handler in it (:25-27). Both decks register in an `$effect` on
mount (`Mp3PlayerView.svelte:569-576`), so a request reaches both: each sets its
own local `showQueue = false`, i.e. it is a browse-to-player navigation, not a
transport command. It starts nothing, seeks nothing, pauses nothing. The only
caller is the MiniPlayer's "return to player" button
(`src/lib/components/ui/MiniPlayer.svelte:267`), reached from the title button
at `:262-272`.

## Q4

The registry is a module-level `_stopFns` object keyed by `AudioSourceId`
(`src/lib/stores/mediaEngine.svelte.ts:37-38`); `registerAudioSource` writes one
entry per id (`:39-41`), and `claimAudio` calls every entry except the claimer's
own, skipping any pair that involves `musicB` (`:43-57`). A registered deck
callback runs `player.stop()` (`Mp3PlayerView.svelte:559-567`), which is
`haltPlayback()` plus `unload()` (`player.svelte.ts:588-591`): `isPlaying` and
`isBuffering` false, `state.currentTime = 0`, `element.pause()`,
`element.currentTime = 0`, then `removeAttribute('src')` and `load()`. The queue
survives, the position does not. Deck ids come from the `deck` prop as
`'musicA'`/`'musicB'` (`Mp3PlayerView.svelte:560`). Five ids are actually
registered today: `musicA` and `musicB` (`Mp3PlayerView.svelte:560`), `podcast`
(`PodcastView.svelte:165`), `radio` (`RadioView.svelte:34`) and `youtube`
(`YoutubePanel.svelte:121`).
`'essay'` and `'mixer'` are in the `AudioSourceId` union (`mediaEngine.svelte.ts:36`)
but nothing registers them.

## Q5

A deck claims two handler slots on the engine, both from `claimMusicControls`
(`Mp3PlayerView.svelte:592-608`): `setPlaybackHandlers(resumePlayback,
pausePlayback, handleSeekSeconds)` and `setSkipHandlers(skipNext, skipPrev)`,
which assign the single module fields `_onPlay`/`_onPause`/`_onSeek`
(`mediaEngine.svelte.ts:320-324`) and `_onNext`/`_onPrev` (:326-329). These are
scalar slots, so the last writer wins; there is no per-deck list. The gate is
`const isMusicView = mediaEngine.displayedSource === (deck === 'A' ? 'A' : 'B')`
(`Mp3PlayerView.svelte:616`), and the claim is called only under it, at `:668`
inside the per-deck engine effect and again at `:739` inside
`syncTrackToMediaEngine`. `displayedSource` returns exactly one of `'A' | 'B' |
'youtube' | 'podcast' | 'radio' | null` (`mediaEngine.svelte.ts:211-247`), so two
decks cannot both pass the gate in the same flush. Two consequences follow from
the code: when `displayedSource` is not a deck (podcasts/radio/YouTube tab) both
decks re-run the effect and skip the claim, leaving the previous deck's closures
in place; and a hidden deck can still act, because the gate tests the engine's
`displayedSource`, not the DOM. The handover is exercised only indirectly, by
the E2E that switches to the B sub-tab and then drives Next to advance Deck B
(`tests/e2e/music-player.test.ts:352-356`); no test asserts slot ownership
directly. Both decks stay mounted at all times as
`display:none` panels (`src/routes/+page.svelte:231-236`, comment at
`:197-205`), and the engine is the only thing that decides which one may claim.

## Q6

The MiniPlayer reads `mediaEngine.displayedSource` (`MiniPlayer.svelte:34-36`)
and addresses playback only through the engine's handler slots: `seekTo` uses
`_onSeek ?? mediaEngine.seek` (:176-179), `togglePlayback` uses `_onPause`/
`_onPlay` (:181-187), `skipPrevious`/`skipNext` use `_onPrev`/`_onNext`
(:189-195). It never names a deck. With both decks playing on the music tab it
shows the visible sub-tab's deck, because `displayedSource` prefers the view's
own source while it plays (`mediaEngine.svelte.ts:227-228`); on a non-music tab
it shows Deck A, since the fallback loop checks `'A'` before `'B'`
(`:244-246`, asserted by the E2E at `tests/e2e/music-player.test.ts:366-369`).
The transport still follows the last deck that claimed the slots, which on a
non-music tab is whichever deck was visible before the tab switch. The speed
control is Deck A only: the button label reads `Playback speed · Deck A`
(`MiniPlayer.svelte:407`, derived at `:174`) and `applyMusicSpeed` writes
`musicSettings.deckASpeed` (:219-223), while the volume row appears only when
Deck B is displayed (:461-476). The deck's own now-playing screen carries no
transport controls, so the MiniPlayer is the only manual pause/seek/skip surface
for either deck (`Mp3PlayerView.svelte:2177-2259`).

## Q7

`FavoriteTracksOptions.startPlayback` is typed at
`src/lib/favorites/favoriteTracks.ts:101-106` as
`(files, index, options?: { selectionLoop?, preserveOrder?, suppressAlert? }) =>
Promise<boolean>`, and `playFavoriteTrack` calls `beginQueue('Favorite Tracks')`
then `startPlayback(files, nextIndex, { preserveOrder: true })` (:263-265). The
view's implementation is `Mp3PlayerView.svelte:1082-1105`: it awaits
`player.play(files, index, { selectionLoop, preserveOrder })` (:1088-1091), bails
on `player.state.error`, then calls `syncTrackToMediaEngine(...)` (:1097), then
sets this deck's engine flag `musicPlayingA`/`musicPlayingB = true` (:1100-1101),
then `claimAudio('musicA' | 'musicB')` (:1103). Before any of that, `beginQueue`
(`:1073-1080`) bumps the per-deck `queueSessionId`, writes the shared
`musicSettings.lastFolderName`, sets `deviceLibrary.trackListLockedByUser` and
sets the global `mediaEngine.musicSelectionLoopActive` to the option default
`false`. So every pre-audio write a favourite start makes is bookkeeping (session
guard, folder label, user-queue lock, loop flag); the playing flag and the
exclusivity claim both come after playback begins.

## Q8

Global (one value for both decks):

- `musicSettings.isRepeat` (`src/lib/stores/settings.svelte.ts:39`), persisted
  under `music-settings`, default `false`.
- `musicSettings.isShuffle` (`:38`), which changes what "next" means but is not
  a loop flag.
- `mediaEngine.musicSelectionLoopActive` (`mediaEngine.svelte.ts:122`, default
  `:191`) and `mediaEngine.musicHasSelectedTracks` (:123, default :192).

Per-deck or per-player-instance:

- The player's own `selectionLoop` snapshot (`player.svelte.ts:156`), written
  only by `loadQueue` from the `PlayerQueueOptions.selectionLoop` option
  (`:69`, `:303`). It is the fallback for `isSelectionLoopActive()` (:166-168).
- `opts.isSelectionLoop`, a live getter the view always supplies
  (`player.svelte.ts:98`, wired at `Mp3PlayerView.svelte:363` to the global
  engine field), so in the app the snapshot is dead and the global wins.
- `selectedBrowseFileKeys` (`Mp3PlayerView.svelte:182`), the per-deck list of
  selected keys the selection loop is built from. It is per-deck but has no
  engine mirror beyond the boolean `musicHasSelectedTracks` (:580).

There is no per-deck repeat flag and no per-deck loop field of any kind. Per-deck
settings exist only for `deckAVolume`/`deckBVolume` (`settings.svelte.ts:35-36`)
and `deckASpeed`/`deckBSpeed` (:51-52).

## Q9

End to end: the element's `ended` listener (`player.svelte.ts:480-490`) clears
`isBuffering`, zeroes `settings.lastTrackTimestamp`, and when
`settings.isRepeat && !isSelectionLoopActive()` sets `element.currentTime = 0`
and calls `safePlay()` (:483-486). It does not look at the queue length and does
not change the queue index. Otherwise it calls `advanceTrack(true)` (:488). The
queue-length case lives one level down in `getNextTrackIndex`
(`src/lib/models/music.ts:284`): `if (trackCount === 1) return isRepeat ||
selectionLoop ? 0 : null`, so a one-track queue with `selectionLoop` on reaches
`advanceTrack` and takes its same-track branch. Note that nothing in the UI
writes `musicSettings.isRepeat` to `true`: the only writers are the
reset-to-defaults in `SettingsView.svelte:423` and the E2E tests seeding
localStorage (`tests/e2e/music-player.test.ts:234,320,397,482,532`). Repeat-one
is therefore reachable today only from persisted or seeded state.

## Q10

The selection loop is the set of browse rows ticked per deck
(`Mp3PlayerView.svelte:884-909`) and turned into a queue by
`preloadLoopSelection` (:915-923): `beginQueue(label, { selectionLoop: true })`,
`player.clear()`, then `player.load(selectedFiles, { selectionLoop: true,
startIndex: 0 })`. It loops over `getSelectedBrowseFilesInOrder()` (:934-950),
i.e. the selected keys in tick order, looked up through the whole library index
first so selections from other folders resolve; `loadQueue` skips the sort when
`selectionLoop` is set (`player.svelte.ts:297`). The only explicit loop toggle
is the MiniPlayer button (`MiniPlayer.svelte:237-246`); ticking a browse row also
writes the flag through `toggleBrowseFileSelection` (`Mp3PlayerView.svelte:904`
and `:907`). Turning the loop off in the MiniPlayer sets
`musicSelectionLoopActive = false` and `musicHasSelectedTracks = false`, and a
view effect then clears that deck's `selectedBrowseFileKeys` when both are false
(`:583-590`). When the selection empties during
playback, `syncLoopTracksToSelection` (`:1372-1393`, called through
`onBeforeAdvance` at `:360`) sets `musicSelectionLoopActive = false` and returns.
Because `onBeforeAdvance` runs for both decks and reads the global flag through
each deck's own selection, a deck whose selection is empty turns the loop off for
the other deck the next time it advances a track. Also note
`toggleBrowseFileSelection` gates on the global `mediaEngine.isPlaying`
(`:890-909`), so while Deck B plays, Deck A cannot preload a loop and only sets
the shared flag.

## Q11

`isRepeat` is read at `player.svelte.ts:51` (interface field), `:351` (passed
into `nextIndex`) and `:483` (the `ended` branch), and at
`YoutubePanel.svelte:392` (YouTube repeat-one); it is written only by the
reset at `SettingsView.svelte:423` and the default at `settings.svelte.ts:39`.
`musicSelectionLoopActive` is written at `Mp3PlayerView.svelte:122, 242, 904, 907,
927, 1077, 1377` and `MiniPlayer.svelte:240, 243`,
`browseNavigation.svelte.ts:249`; read at
`Mp3PlayerView.svelte:363, 585, 1344, 1350, 1373`, `MiniPlayer.svelte:238-296`,
and `tests/unit/browse/browseNavigation.test.ts:359-366`. Because both decks pass
the same `musicSettings` object into `createPlayer` (`Mp3PlayerView.svelte:350`)
and read the same engine fields, a single `isRepeat` value drives every deck: set
it for Deck A and Deck B repeats one track too, and neither deck can have
repeat-one while the other wraps. The two fields that would have to change owner
are `musicSettings.isRepeat` and `mediaEngine.musicSelectionLoopActive`; the
second is already close to per-deck, since the selected-keys list and the queue
built from it are per-deck, with only the flag and `musicHasSelectedTracks`
global. Whether those fields
should move is a design decision; the code does not express one.

## Q12

At the end of a one-track queue with neither repeat nor selection loop,
`nextIndex` returns `null` (`music.ts:284`), and `advanceTrack` takes the
`next === null` branch: `haltPlayback()` then `return false`
(`player.svelte.ts:406`), i.e. `isPlaying = false`, `isBuffering = false`,
`state.currentTime = 0`, element paused and rewound (`:230-238`). The queue and
the element's `src` stay. On the same-track loop branch (`:408-421`) it calls
`setCurrentTrack(next)`, sets `state.currentTime = 0` and
`settings.lastTrackTimestamp = 0`, then either reloads the src when the element
is in an error state or sets `el().currentTime = 0`; if `wasPlaying` it clears
`isBuffering` and calls `safePlay()` (`:419`), which keeps the element playing,
so `isPlaying` stays true and only the position restarts at 0. It returns
`false`, so the view does not re-claim the audio channel for this path
(`Mp3PlayerView.svelte:1417-1421`).

## Q35

`claimAudio` invokes every registered stop callback except the claimer's, with
one documented exception hard-coded twice in the loop: `if (id === 'musicB' ||
other === 'musicB') continue` (`mediaEngine.svelte.ts:46-50`). The exception is
Deck B, the mixing deck, spelled out in the module header (`:21-33`, code at
`:48`) and in the state spec invariant
(`docs/state/audio-playback-lifecycle.md`, "Deck B is the mixing deck"). So a podcast claim (`podcastPlayer.ts:184, 397, 455`), a radio
claim (`RadioView.svelte:112`, and `playStream`'s own `claimAudio('radio')` at
`mediaEngine.svelte.ts:370`) or a YouTube claim (`YoutubePanel.svelte:251, 455`)
runs Deck A's stop callback (`player.stop()`) and leaves Deck B playing. A
non-radio, non-Deck-B claim also tears down the engine-owned radio stream
(`:53-56`). The same rule protects both directions: a Deck A claim
(`Mp3PlayerView.svelte:1103`) stops podcast/radio/YouTube but never Deck B, and a
Deck B claim never stops anything. The E2E suite pins both halves: radio stops
Deck A (`tests/e2e/music-player.test.ts:466-511`) and radio does not stop Deck B
(`:513+`).

## Q36

Order is: set this source's own playing flag first, then claim. The engine's
`isPlaying` is derived from the per-source flags (`mediaEngine.svelte.ts:203-206`)
and `pause()` calls `markUserPaused()` before dispatching (`:265-267`), so a claim
that ran first would stop other sources while this source's flag was still false
and `isPlaying` would transiently drop. The deck does exactly that in
`startPlayback` (`Mp3PlayerView.svelte:1099-1103`), in `resumePlayback`
(`:1360-1365`, same comment), and in `claimDeckAudioForSkip` (`:1407-1415`); the
comments at `:1099` and `:1360-1361` state the reason. Other sources follow the
same convention: podcast (`podcastPlayer.ts:394-397`), YouTube
(`YoutubePanel.svelte:247-251`), radio (`mediaEngine.svelte.ts:366-370`). Two
further details matter for exclusivity: the deck only claims when playback
actually began, so `skipNext`/`skipPrev` gate the claim on the promise resolving
true (`Mp3PlayerView.svelte:1417-1429`), and `player.stop()` from a foreign claim
only unloads, so a later `resume()` re-enters at the start of the selected track
because `element.src` is empty (`player.svelte.ts:593-605`).

## Q37

The single knob is the pair of handler slots `mediaEngine._onPause` and
`_onPlay`, which only the deck whose `displayedSource` matches ever writes
(`Mp3PlayerView.svelte:616, 668, 739`). Every pause path goes through them and
therefore pauses exactly one deck: the sleep timer
(`src/lib/stores/sleepTimer.svelte.ts:28-35`, `mediaEngine._onPause?.() ??
mediaEngine.pause()`), the MiniPlayer (`MiniPlayer.svelte:181-187`), the web
MediaSession pause action (`mediaEngine.svelte.ts:602-604`) and the native
`mediaAction` pause (`:825-830`). The other deck keeps playing. Two global side
effects ride along regardless of deck: `mediaEngine.pause()` calls
`markUserPaused()` (`:265-267`), which clears the single `_userWantsPlayback`
latch (`:89-93`) that Android background recovery is gated on (`:719, 761`), and
that latch is re-set by the `isPlaying` effect (`:776-778`). Nothing in `src/`
pauses a named deck: the only route into `pausePlayback` is the engine slot
itself (`Mp3PlayerView.svelte:596`).
