# Research: section 4, how the index, browse list, search index and queue react to mutation

Stage: R (Research). Tree: `main`, working tree read-only. Answers Q24 to Q29 of
`.scratch/library-delta/questions.md`. No design proposals.

Svelte version in this tree is 5.53.12 (`package.json:44`). The reactivity statements
below follow Svelte 5 proxy semantics: reading `allFiles.length` subscribes the reader to
the `allFiles` variable and to the proxied array's `length`; an index write notifies only
readers of that index. No test in `tests/` exercises these two effects (grep for
`searchIndex`, `_searchIndex`, `mergeSortedIndex` returns nothing), so the behaviour is
read from the code, not from a test.

---

## Q24

The reload effect is `src/lib/components/views/Mp3PlayerView.svelte:785-791`. Its own
reactive reads are `browsePath` (`:786`), `driveSearch` (`:787`), `browseVersion` (`:788`)
and `musicSettings.librarySource` (`:789`). Because it calls `loadBrowseEntries`
synchronously, every read the loader makes before its first `await` also becomes a
dependency of this effect: `musicSettings.librarySource` and the drive filter
(`src/lib/browse/browseNavigation.svelte.ts:112`), `musicSettings.sortOrder` in the
drive-search branch (`:115`), `allFiles.length` (`:122`), every element of `allFiles`
(`buildBrowseEntries` iterates the array at `src/lib/models/browse.ts:20`, called at
`browseNavigation.svelte.ts:123`), and `deviceLibrary.nativeTreeUri` (`:127`, `:176`) and
`deviceLibrary.rootDirHandle` (`:146`). `libraryScanPromise` is read at `:124` but is a
plain `let` (`src/lib/device/deviceLibrary.svelte.ts:140-141`), deliberately not
`$state` as the comment at `:136-139` states, so it never re-triggers a reload. Reads
after an `await` (`browseNavigation.svelte.ts:129`, `:177`) are not tracked at all.

The reload fires on both signals. `bumpBrowseVersion` is called per scan batch
(`deviceLibrary.svelte.ts:179`) and on many other transitions, and every `allFiles` write
also re-runs the effect because the loader reads the array. A device batch does both in
the same tick (`:178-179`), which Svelte coalesces into one reload. The scan-end
assignment at `:194` has no bump and still reloads through the `allFiles` read. Nothing
triggers a reload when `libraryScanPromise` settles; only `allFiles` or `browseVersion`
changing does. Overlapping loads are dropped by the per-instance `browseLoadId`
(`browseNavigation.svelte.ts:106`, `:109`, checked at `:130`, `:178`, `:197`).

## Q25

Counts come from `buildBrowseEntries` (`src/lib/models/browse.ts:15-41`). Folders are
derived from path prefixes of the files, and `count` is the number of indexed files whose
relative path continues under that folder name at any depth (`:30-31`, `:34-38`). No
filesystem child count is involved.

The live branches set `count: 0` for native folders: the mid-scan single-level listing at
`browseNavigation.svelte.ts:135` and the full live listing at `:184`. The web
`rootDirHandle` branch is the only one that computes a real count, by iterating the child
directory one level deep (`:162-168`).

Which branch wins is decided at `browseNavigation.svelte.ts:122-126`. The snapshot from
the index wins when it has at least one entry for the current path, or when
`libraryScanPromise === null` (`:124`). The live `listEntries` call only runs when the
snapshot is empty for this path, a scan promise exists and `nativeTreeUri` is set
(`:127-129`). With a partial index, a folder that has no indexed files yet does not appear
at all, because `buildBrowseEntries` only creates a folder entry for a file it actually
saw (`browse.ts:30-31`); folders with some indexed files show a partial count.

## Q26

Line by line, the effect is `Mp3PlayerView.svelte:244-274`. `:245` reads
`allFiles.length` into `total`. `:249` zeroes `_searchIndexSortedLength` when `total` is
below it. `:250` returns immediately when `total` equals the tracked length. `:251-255`
clears the index when `total` is 0. `:259-263` does the full rebuild when the tracked
length is 0. `:265` slices the tail `allFiles.slice(_searchIndexSortedLength)`, `:266`
sorts that slice (through the local wrapper at `:899-900`, which passes
`musicSettings.sortOrder`), `:271` merges, `:273` records `total`. `mergeSortedIndex`
(`:276-299`) is a plain two-way merge of two already sorted arrays keyed by
`musicSettings.sortOrder` (`:282-286`), comparing with
`localeCompare(..., { numeric: true })` (`:290`), with no dedupe of any kind.

Every `allFiles` write in the tree is a whole-array assignment, never a mutation of the
existing array. Sites: `Mp3PlayerView.svelte:1222`, `:1567`, `:1590`;
`deviceLibrary.svelte.ts:163`, `:178`, `:194`, `:251`, `:258`, `:269`, `:285`, `:294`,
`:332`, `:344`, `:375`, `:383`, `:401`, `:428`, `:451`, `:458`, `:572`;
`driveLibrary.ts:235`, `:248`, `:260`, `:270`, `:467`, `:474`; `fileOps.ts:213`. The one
in-place write is on the scan's own accumulator, `collectedFiles.splice` at
`Mp3PlayerView.svelte:1178-1180`, before that array is assigned to `allFiles`.

What the index does per case:

1. **Append, prefix unchanged** (`deviceLibrary.svelte.ts:178`, `:572`;
   `driveLibrary.ts:270`). Tail slice at `:265`, sort and merge at `:266-271`. Correct as
   long as the first `oldLength` entries are unchanged.
2. **Replace with a longer array whose prefix differs** (`deviceLibrary.svelte.ts:194`,
   `Mp3PlayerView.svelte:1222`, `driveLibrary.ts:248`). Same tail-slice path, but the new
   array's first `oldLength` entries are never indexed. `playNativeFolderFromScan`
   assigns a folder-only list at `Mp3PlayerView.svelte:1222`; if that folder holds more
   files than the previous whole-library index, the result is the old library index plus
   the folder's files from position `oldLength` on, and the folder's first `oldLength`
   files are absent from search.
3. **Replace with a shorter array** (`fileOps.ts:213`, `deviceLibrary.svelte.ts:163`).
   `:249` zeroes the tracked length, so `:259` takes the full rebuild and the index is
   rebuilt from the actual array.
4. **Replace with an equal-length array of different contents.** `:250` returns before
   reading any element, so the index is neither rebuilt nor re-sorted. It keeps the
   removed files (search still finds them, and result rows carry the old file objects,
   `Mp3PlayerView.svelte:313-320`) and misses every new one. Live paths that can hit
   this: the Drive background refresh replacing a cached list (`driveLibrary.ts:235`,
   `:248`), the web file inputs (`deviceLibrary.svelte.ts:401`, `:428`), and any rescan
   whose removals and additions balance out between two effect flushes.
5. **In-place element replacement (`allFiles[i] = x`).** No code does this today. If it
   did, the effect reads only `length` before the guard, so an index write notifies
   nothing the effect subscribed to and the index stays stale.
6. **In-place append or splice.** No code does this today. A `$state` proxy notifies the
   `length` source, so the effect would re-run and take the tail-slice path (append) or
   the shrink reset (splice).
7. **Shrink by one and grow back by one inside one flush.** Only the final length is
   observed, so this is case 4: the removed entry stays and the added entry is missing.
8. **Empty array.** `:251-255` clears the index and the tracked length.

Two more facts read from the merge body. `mergeSortedIndex` compares with
`{ numeric: true }` (`:290`) while the full-build sort uses plain `localeCompare` for the
`title` and `artist` orders (`src/lib/models/music.ts:222-225`), so a merged index can end
up in a different order than a rebuild would produce. And nothing in the merge dedupes by
key, so a duplicate key arriving in the tail is kept twice. Separately, changing
`musicSettings.sortOrder` alone re-runs the effect (the sort wrapper reads it at
`Mp3PlayerView.svelte:900`), but the guard at `:250` returns, so the existing index keeps
the order it was built with.

## Q27

Five things react to a shrink, none to array identity:

- `forgetDeletedFile` (`src/lib/files/fileOps.ts:209-222`) filters by
  `getStoredFileKey`, compares lengths at `:212` and assigns at `:213`. Contents plus
  length. It then rewrites the cache (`:218-220`) or deletes the keys (`:224-226`).
- The search-index reset (`Mp3PlayerView.svelte:246-250`). Length only: a shrink below the
  tracked length sets it to 0, which forces the full rebuild at `:259`.
- The selection pruning effect (`Mp3PlayerView.svelte:793-811`). It reads
  `allFiles.length` (`:799`) and maps every element to a key set (`:800-802`), so it
  depends on contents and length, not identity. Keys that no longer resolve are dropped
  (`:803-810`).
- The browse reload (`Mp3PlayerView.svelte:785-791`) through the loader's `allFiles`
  read (`browseNavigation.svelte.ts:122-123`).
- `hasFolderLoaded` (`Mp3PlayerView.svelte:589`), length only.

Nothing reacts to a shrink by touching the queue or `currentIndex`.
`hydrateTracksFromLibrary` is only called from explicit flows
(`Mp3PlayerView.svelte:1569`, `deviceLibrary.svelte.ts:196`, `:259`, `:296`, `:345`,
`:384`, `:406`, `:433`, `:459`, `driveLibrary.ts:475`), never from an `allFiles` effect.
No consumer compares array identity: grep for `=== allFiles` finds nothing.

## Q28

`hydrateTracksFromLibrary` (`Mp3PlayerView.svelte:116-146`) sorts the incoming list,
clears the player when it is empty (`:120-125`), resets to track 0 when asked
(`:127-133`), otherwise resumes by `musicSettings.lastTrackKey` and falls back to
`musicSettings.lastTrackIndex` (`:138-145`). It is called at scan end only when
`trackListLockedByUser` is false (`deviceLibrary.svelte.ts:196`), and `beginQueue` sets
that lock true on every user-started queue (`Mp3PlayerView.svelte:1106`). `beginQueue`
also bumps `queueSessionId` (`:1104`), and `appendTracksToQueue` refuses to append when
the session changed (`:1150`).

The player's public surface is `state`, `play`, `load`, `append`, `clear`, `stop`,
`pause`, `resume`, `next`, `prev`, `seek`, `destroy` (`src/lib/audio/player.svelte.ts:530`,
`:538`, `:541`, `:578`, and the tail of the returned object). There is no remove and no
in-place update. `load` replaces the queue via `loadQueue` (`:292-330`), `append` merges
(`:541-575`) by `getTrackKey` through `mergeStoredFiles` (`:547`), and returns early when
nothing is new (`:548`); it reuses url, duration and cleanup for keys already queued
(`:550-566`).

The queue holds a copy, not the `allFiles` array: `loadQueue` maps the files into new
`PlayerTrack` objects (`:299-302`) with `source: f`, keeping the same file objects in a
new array. A later `allFiles` write never reaches `state.tracks`, so a file deleted from
the index stays in the queue and stays playable until the queue is replaced.

## Q29

The identity key is `getStoredFileKey` (`src/lib/models/music.ts:114-117`): `d:<fileId>`
for Drive, `n:<relativePath>` for native, `w:<relativePath>` for web; `getTrackKey` is an
alias (`:120-122`). A rename or move therefore changes the key for native and web files
(`relativePath` changes) and keeps it for Drive files, whose key is the Drive file id.

Consumers that treat a renamed native or web file as a different file: favourites, which
store the key (`src/lib/favorites/favoriteTracks.ts:133`) and later resolve it against
`allFiles` and the queue (`:166-167`); the browse selection set
(`Mp3PlayerView.svelte:801-802`, `:911-915`); the resume key, written by
`setCurrentTrack` (`player.svelte.ts:217-221`) into `musicSettings.lastTrackKey`
(`src/lib/stores/settings.svelte.ts:46`) and read at `Mp3PlayerView.svelte:138-139`; the
queue merge (`player.svelte.ts:547-559`); `forgetDeletedFile`
(`src/lib/files/fileOps.ts:210-213`); and the current-track highlight
(`Mp3PlayerView.svelte:2028`). `mergeStoredFiles` (`music.ts:230-241`) is first-wins by
key: an appended renamed file is added as a second entry and the old entry is never
removed, because no merge path reports absence.

Nothing here is unresolved.
