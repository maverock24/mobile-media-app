## Q39

Six test files constrain a change to the scan, the cache payload or the index
mutation. Each entry is the test title, the location, and what it asserts.

### The scan (`tests/unit/device/deviceLibrary.test.ts`, `tests/unit/browse/folderScan.test.ts`)

- **`startLibraryScan` › "streams a native scan batch by batch, bumping the browse version and progress"** (`tests/unit/device/deviceLibrary.test.ts:223`). Drives a fake scan whose `onBatch` fires once, then asserts four things: the scan was called as `scanNativeAudioFiles('content://tree', [], 500, {}, fn)` (`:241`), `lib.scanProgress` observed inside the batch callback equals `{ pct: 99, filesFound: 1 }` (`:232`, `:242`), `view.allFiles` ends as `['a.mp3']` (`:243`), and `bumpBrowseVersion` was called at least once (`:245`). The `pct: 99` value is computed inside the same callback that writes `allFiles` and calls the bump (`src/lib/device/deviceLibrary.svelte.ts:178-182`), so the assertion at `:245` is the one that fails if the per-batch bump goes away: nothing else in that code path calls the sink (`deviceLibrary.svelte.ts:161-206`; the reset bump at `:164` only fires when `resetExistingFiles` is set, and this test does not set it).
- **"clears the existing list first when resetExistingFiles is set"** (`deviceLibrary.test.ts:248`). Asserts `allFiles` is emptied before the scan (`:255`), the sink is called with no arguments (`:256`), and `scanProgress` is reset to `{ pct: 0, filesFound: 0 }` (`:257`). Pins the reset shape and the no-argument sink signature.
- **"leaves the queue alone while trackListLockedByUser is set"** (`deviceLibrary.test.ts:261`). Asserts the completion path does not call `hydrateTracksFromLibrary` when the lock is set.
- **"scans a web directory handle, stores the result and hydrates the queue"** (`deviceLibrary.test.ts:207`). Asserts the cache write is exactly `saveCachedLibrary(null, 'Music', view.allFiles)` (`:218`), so the web path passes a null tree URI and the whole list.
- **`scanNativeAudioFiles` › "collects every batch and reports progress until done"** (`tests/unit/browse/folderScan.test.ts:143`). Asserts the concatenated result order (`:153`), two `onBatch` calls (`:154`), the exact per-batch state objects including cumulative `foldersScanned`/`foldersQueued`/`totalFiles` (`:155-156`), and that a completed scan is never cancelled (`:158`).
- **"passes the browse path through as a joined string"** (`folderScan.test.ts:161`), **"uses initialBatchSize for the first batch and batchSize afterwards"** (`:168`), **"clamps a zero or negative initialBatchSize up to one"** (`:178`), **"does not report an empty batch to onBatch"** (`:185`). These pin the `startAudioScan` argument shape, the two batch-size rules and the empty-batch suppression.
- **"cancels the scan when a batch rejects"** (`folderScan.test.ts:197`). Asserts the original error is rethrown and `cancelAudioScan({ scanId: 's1' })` was called (`:202-203`).
- **"swallows a cancellation failure and still rejects"** (`folderScan.test.ts:206`). Asserts the reject survives a failing cancel and that it is warned, not thrown (`:212-213`).

### The cache payload (`tests/unit/browse/libraryCache.test.ts`, `tests/unit/utils/idb.test.ts`)

- **"round-trips a native library under its tree-URI key"** (`tests/unit/browse/libraryCache.test.ts:212`). Asserts `loaded.folderName === 'Music'` (`:215`) and asserts the loaded file array with a strict `toEqual` against one object carrying exactly `source, name, relativePath, path, mimeType, modifiedAt` (`:216-218`). This is the test that breaks if a defined field is added to `CachedNativeLibraryFile`.
- **"mirrors the write under the last-library key"** (`libraryCache.test.ts:221`), **"rejects the last-library mirror when the folder name differs"** (`:229`), **"writes nothing for an empty library"** (`:234`), **"drops drive entries, so a drive-only library writes nothing"** (`:239`), **"loads nothing for a folder that was never cached"** (`:245`), **"uses an explicit cache key when one is passed"** (`:249`). These pin key derivation, the double write, the folder-name guard on the fallback, the empty and drive-only early returns (`src/lib/browse/libraryCache.ts:83`), and that the mirror is written for any non-last key (`:88-90`). The explicit-key test only checks `not.toBeNull()` on the raw read (`:252-255`), so it does not pin the payload object's top-level shape.
- **"rehydrates native entries as stored native files"** (`libraryCache.test.ts:183`). Strict `toEqual` on the reconstructed `StoredAudioFile` with exactly the six native keys (`:185-193`), so a new field that propagates through `restoreStoredFilesFromCache` (`src/lib/browse/libraryCache.ts:115-129`) also breaks here.
- **`library cache` › "load returns null before any save"** (`tests/unit/utils/idb.test.ts:49`) and **"delete is a no-op on a missing key"** (`:53`). Pin only the empty-key behaviour of the raw store.
- Run confirmation: `npx vitest run tests/unit/browse/libraryCache.test.ts` passes, 40 tests.

Answering the three hypotheticals directly:

- Batches stop bumping `browseVersion`: fails `deviceLibrary.test.ts:245` and, if the progress write went with it, `:242`.
- Rescan stops clearing the cache: fails `deviceLibrary.test.ts:285` and `:299`, which assert the exact ordered `deleteCachedLibrary` argument list `['device:content://tree', 'last-library']` and `['device-folder:Library', 'last-library']`.
- The cache payload gains fields: fails `libraryCache.test.ts:216-218` and `:185-193` if the field lands on a cached file entry and survives restore. A new top-level key on `CachedLibrary` (`src/lib/models/music.ts:68`) fails nothing in this set.

### The index mutation (`tests/unit/files/deleteUpdatesView.test.ts`, `tests/unit/browse/browseNavigation.test.ts`)

- **"drops the deleted local row and keeps the rest"** (`tests/unit/files/deleteUpdatesView.test.ts:103`). Asserts the browse list before the delete (`:106`), then after `runPendingFileOp` that `browseEntries` is `['keep.mp3']` (`:112`) and `deck.allFiles` equals exactly `[keeper]` (`:114`). Pins that a delete rewrites `allFiles` and that the browse view reacts.
- **"drops the deleted Drive row and leaves the Drive listing intact"** (`deleteUpdatesView.test.ts:117`). Same assertions for the drive source.
- **"builds entries from the file snapshot with folders before files, numerically sorted"** (`tests/unit/browse/browseNavigation.test.ts:133`). Pins folder-before-file ordering and numeric name sort in `buildBrowseEntries` (`:144-149`).
- **"uses the snapshot even while an index scan is in flight when it has entries for the path"** (`browseNavigation.test.ts:151`). Asserts the snapshot wins and `listEntries` is not called (`:159-160`).
- **"live-lists through the tree URI when the path is not yet indexed and a scan is in flight"** (`browseNavigation.test.ts:163`). Asserts the live listing is called with `{ treeUri, path: 'sub' }` and its folders and files are separately sorted (`:175-178`). Together with the previous test this pins the completeness test at `src/lib/browse/browseNavigation.svelte.ts:124` (`snapshot.length > 0 || libraryScanPromise === null`).
- **"walks a File System Access root handle, counting files and wrapping audio"** (`browseNavigation.test.ts:183`) pins the web live branch and its folder counts; **"lists native audio through the tree URI when allFiles is empty"** (`:197`) pins the empty-index fallback.

the two Capacitor templates:

- `android/app/src/test/java/com/getcapacitor/myapp/ExampleUnitTest.java:12-18`:
  one test, `addition_isCorrect`, asserting `4 == 2 + 2`. Nothing imports or

  `"com.getcapacitor.app"` (`:24`). The app's `applicationId` is

There is no test double for the provider layer. A repo-wide grep for
`robolectric`, `MockCursor`, `shadowOf` and `mockito` (excluding `node_modules`
and `*/build/`) returns no matches. The test dependencies are the stock Capacitor
set: `testImplementation "junit:junit"` and `androidTestImplementation
androidx.test.ext:junit` plus `espresso-core` (`android/app/build.gradle:108-110`).

No JavaScript test reads the plugin source: no `.ts` test file references
`android/app/src/main` or any `.java` path (grep over `tests/**/*.ts` returns
nothing), and `tests/unit/native/` does not exist. The JS side mocks the bridge
module instead, for example `tests/unit/device/deviceLibrary.test.ts:33-39`.

The only automated guarantee about the plugin's shape is the CI DEX check:
`.github/workflows/quality.yml:117` reads the minified benchmark APK and fails if
`DirectoryReaderPlugin` or any of its listed methods is missing. See Q41.

## Q41

The repo `AGENTS.md` claim is wrong and `quality.yml` is right. `quality.yml`
triggers on both events, `push` to `main` and every pull request:

- `.github/workflows/quality.yml:3-5` (`on:`, `push:`, `branches: main`)
- `.github/workflows/quality.yml:7` (`pull_request:`)
- `.github/workflows/quality.yml:50` (`android-release-compile:` as a top-level
  job). Grep for `if:` and `needs:` over the whole file returns no match, so the
  job has no condition and no gate: it runs on every run of the workflow,
  including pull requests.

That job compiles Java on a pull request. Its steps: `./gradlew assembleRelease`
at `:96-100`, `./gradlew :app:assembleBenchmark :benchmark:assembleBenchmark` at
`:105-108`, and the DEX assertion at `:117-201`, whose `CLASSES` list is at
`:169` and whose `METHODS` map is at `:170-177`; the
`DirectoryReaderPlugin` line at `:171` names `rememberTreeUri`, `startAudioScan`,
`getAudioScanBatch`, `cancelAudioScan`, `listEntries`, `listAudioFiles`,
`writeFile`, `appendFileChunk`, `deleteEntry`, `copyEntry`, `moveEntry`,
`installApk`. The check requires the class descriptor, a no-arg `<init>()V`, and
each of those names to appear in the dexdump of the minified APK (`:179-196`).

`AGENTS.md:26` says "No workflow compiles Java on a pull request". The other
workflows are consistent with the rest of that sentence but do not rescue it:
`netlify-deploy.yml:3-9` runs on push to `main` and on `workflow_dispatch`,
`android-release.yml:3-5` on version tags, `android-build.yml:3-4` on
`workflow_dispatch` only. Only `quality.yml` has a `pull_request` trigger, and it
does compile Java.

No Java test is executed anywhere in CI: the only Gradle invocations across all
four workflows are `assembleDebug` (`android-build.yml:60`), `assembleRelease`
(`android-release.yml:102`, `quality.yml:100`), `assemble<variant>`
(`netlify-deploy.yml:134`) and the two benchmark tasks at `quality.yml:108`.
No workflow runs `test`, `testDebugUnitTest`, `connectedAndroidTest` or `lint`.

The JS side of a pull request, in the `validate` job (`quality.yml:14-48`):
`pnpm check` (`:39`), `pnpm test` (`:42`), `pnpm test:e2e` (`:48`). `pnpm test`
is `vitest run` (`package.json:21`), which by config includes only
`src/**/*.{test,spec}.{ts,js}` and `tests/unit/**/*.{test,spec}.{ts,js}`
(`vite.config.ts:38`), with `tests/unit/setup.ts` as setup (`:39`). `pnpm

## Q42

There is no ADR and no state spec for the library index or the scan lifecycle.

`docs/adr/` holds three files, all Accepted, none about scanning or caching:
`0001-player-module.md:1` (extract the playback core into a `player` module),
`0002-file-move-copy-delete.md:1` (native move/copy/delete in the browse view),
`0003-youtube-audio-playback.md:1` (YouTube audio through CapacitorHttp).
Scanning appears in `0001-player-module.md:11` and `:49` only as part of the list
of concerns the view keeps, not as a decision. `0002-file-move-copy-delete.md`
describes move/copy/delete and never mentions the library cache, even though
`src/lib/files/fileOps.ts` rewrites it.

`docs/state/_index.md:5-8` lists exactly four machines: Audio Playback
Lifecycle, Google Drive Auth, Sleep Timer, YouTube Playback Lifecycle. None of
the four specs (`audio-playback-lifecycle.md`, `google-drive-auth-sync.md`,
`sleep-timer.md`, `youtube-playback.md`) covers the scan or the cache: grep for
`scan` across `docs/state/` returns no match, and across `docs/adr/` returns only
the two incidental mentions in `0001-player-module.md`.

The nearest prose is `docs/refactoring-plan.md:143-158`, which records the
`libraryCache` extraction and lists the helpers and the changed signatures. It is
an extraction record, not a decision or a state spec.

The repo's stated placement rule is `AGENTS.md:25`: decisions go in `docs/adr/`,
runtime state machines in `docs/state/`. `docs/state/_index.md:10` states the
format those specs follow (State Spec v1: flat transition tables, closed-world
contract, invariants and forbidden transitions, code-reconciled). No file under
either directory describes the scan lifecycle or the cache at present.
